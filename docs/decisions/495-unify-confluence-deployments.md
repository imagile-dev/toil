# One CLI and MCP surface per product: Confluence Data Center and Cloud (#495, slice 2)

The maintainer's decisions on #495 and slice 1's defaults (`495-unify-jira-deployments.md`) apply unchanged. These are the defaults this slice chose within them.

- **Paging keeps both flags, each refused on the other deployment.** Data Center pages by `--offset` (a position the contract records for `page list` and `page search`); Cloud pages by `--cursor` (an opaque token, `meta.page.nextCursor`). Data Center sets no `meta.page` today, and an offset is not a cursor: accepting `--cursor` on Data Center would mean inventing a token format for a position the server counts for us. So they are two ideas, not one idea in two spellings (principle 10), and `UNSUPPORTED` before any request names the flag and the deployment that takes it. `space list --cursor` is Cloud's alone for the same reason (Data Center's space list has no offset, as recorded). No divergence is needed: Data Center's recorded paths, flags and behaviour are unchanged.
- **Flags that were only on one deployment stay there.** `page get --expand` and `page create|update --markdown` are Data Center's (v2 has no expansions; Cloud documents no synchronous Markdown converter). Each is `UNSUPPORTED` on a Cloud connection, naming the flag.
- **`check-dossier` stays Data Center's.** Cloud had no such command and none is added here; on a Cloud connection it is `UNSUPPORTED`. It is also the one command in this pair a deployment lacks, which keeps the parity suite's refusal checks proving something.
- **Shared token: one rule, `fallbackWhen(jira, own)`.** Slice 1 wrote one function per area (Data Center: Jira is not Cloud; Cloud: Jira is Cloud). With one area, the default connection takes Jira's default connection's env token only when the two have the same deployment, judged from both as they resolve (`defaults.<area>` and the area's default included). `fallbackWhen` therefore receives the borrowing connection's settings as a second argument. An explicit `apiTokenFrom` is still the user's call and is not asked. Slice 1's tests keep their substance, with one test per direction on each side: Jira Cloud's token is not lent to Data Center Confluence, Jira Data Center's is not lent to Confluence Cloud, and like pairs lend.
- **The config fold runs for every version, and is idempotent.** Slice 1 folded only files older than version 3, so a version 3 file written by slice 1's toil that still said `confluence-cloud` (slice 1 left it a separate area, and a user could have named a connection that way after it) was only warned about as an unknown area. Every saved file is version 3, so waiting for the next version was no option. The fold now runs on every read. It changes nothing on a second run: a folded file has no connection of the old area and no `defaults` entry for it, which is the whole of its trigger. Files older than version 3 fold quietly, as they did, since they meant the old area. A version 3 file folds with a `CONFIG_RENAMED_AREA` warning (one per old area, naming the connections and defaults moved and the new form), because toil wrote that name or a person typed it after the area was gone, and a person should hear it once.
- **`jira-cloud` in a version 3 file now folds too, the same way (consistency with slice 1).** Slice 1 left the version 3 case as a `CONFIG_RENAMED_AREA` warning and an unusable connection (`warnUnknownAreas`). Folding is the friendlier of the two and the warning code stays, so that branch of `warnUnknownAreas` is gone, and the config test, `skills/toil/jira.md` and slice 1's decisions file say so.
- **Cloud's `data` is Cloud's.** `bodyText`, the version list for `page history` and the typed `children` stay as Cloud returns them, and `meta.context.connection.deployment` says which ran. The contract test holds Data Center's examples to the recorded field names only.
- **Descriptions are said once for both**, in `src/areas/confluence/overrides.ts`: the tool description of each command names what each deployment returns, so an agent that reads one description does not use half of it on the other. Field help that differs (`--body`, `--representation`, `--status`, `--limit` on search) is worded once, and a field on one deployment only gets `[Data Center only]` or `[Cloud only]` appended by the fold. The attachment id's wording is one constant in `area.ts`, because positional arguments are compared as written and cannot be overridden.
- **`CONFLUENCE_CLOUD_ATTACHMENT_HOST` keeps its name.** It is a warning code Cloud's download raises (Data Center raises `CONFLUENCE_ATTACHMENT_HOST`); codes are an open set and a code that says which API a warning came from is information, not leftover.
- **`dossiers show` reports the connection's `deployment`,** for an area whose variants are keyed on it, as an additive field of `areas.<area>.connection`. Toil UI's worklog export offers a Confluence page with `--markdown`, which Cloud refuses, and had no way to know which kind of Confluence the dossier's connection is. It offers nothing on a Cloud connection now.
- **The retired names are the table's, as for Jira:** `RENAMED_AREAS` gains `confluence-cloud`, which retires `TOIL_CONFLUENCE_CLOUD_*`, `TOIL_CONN_<NAME>_AREA=confluence-cloud`, `--areas confluence-cloud`, `toil confluence-cloud …`, `confluence_cloud_*` tools and `confluence-cloud` dossier sections (also under an environment and in `people[].ids`) in one line, each with the new form. Stale `TOIL_CONFLUENCE_*` on a Cloud default is refused unless `TOIL_CONFLUENCE_DEPLOYMENT` is set, and an empty retired variable is skipped unless `TOIL_STRICT_ENV=true`.
- **`CONTRACT_VERSION` stays 2.** The only toil tag is `v0.1.0-beta.2`, which does not contain #499 (still open), so one release carries every slice and the version is raised once for all of them. The contract's row 2 now names both areas.
- **The site and skill have one Confluence page and one verification level (`unit`).** `confluenceSupported` keeps Data Center's floor (7.9) and says in its note that Cloud is always current. `skills/toil/confluence-cloud.md` and the Cloud site data files are deleted, and the README's "Docs and design" count drops to 3.
- **Nothing here uses a generic hyphenated area for tests but `demo-cloud`.** The config and triage tests used `confluence-cloud` (slice 1's stand-in once `jira-cloud` was retired) to prove the longest-match env rule and the path check; both now use `demo-cloud`, an area that exists nowhere, so retiring another real one does not break them again.
- **Not done:** no Windows, macOS or Node 26 run was made for this slice, and nothing was run against a live Confluence of either kind.
