# `github project status`, and the board proposing it (#561)

- **One command, `toil github project status [project] [number] --to <status>`, sets the Status single-select field of one Projects (v2) item** (`src/areas/github/projects.ts`). The Board's drag-to-move for a GitHub item used to say toil had no such command; it now proposes this one. Only Status, not any field: the board's columns are Status, and a general field setter is a larger surface (types, iterations, dates) nobody asked for.
- **The status is named by option name, case-insensitive, and resolved against the project's own Status options.** An unknown name is `INVALID_INPUT` listing the real options, as `jira issue transition --to` does for a transition. Names, not ids, because the board's cards already carry the option's name (`status`).
- **The item is named one of two ways, and the two are exclusive.** `<project> <number>` (with `--owner` and `--repo`) finds the issue's or pull request's item on that project; `--item <PVTI_…>` names it directly and needs neither. `--item` exists because the Toil UI knows the board item's id (it is in the `project items` output the item was mapped from) but not the project's number, which lives in the Toil project's `github.projects` list, not on the item. Both ways read the item, its project and the project's Status field in one GraphQL request, so the mutation is the second and last request.
- **An issue that is not on the project is `NOT_FOUND` with a fix, never added.** Adding an item is a second write the person did not ask for. The message says which projects the issue is on.
- **A project owned by someone other than the repository's owner needs `--item`.** `--owner` is both the project's owner and the repository's, as everywhere in this area, so the number form cannot say otherwise.
- **An item already at that status sends nothing and says `changed: false`.** The write gate still applies first, so it needs `writes` and `--allow-write` like any call. Skipping the mutation avoids an `updatedAt` bump on a no-op.
- **Scopes (not confirmed against a live token).** A classic token needs `project` (which includes `read:project`) to change a project item; a fine-grained token needs Projects (organization) at Read and write, and cannot reach a user's own projects. Derived from GitHub's documentation for `updateProjectV2ItemFieldValue`, which no real account has exercised here: `src/areas/github/scopes.ts` lists both, and the command's `AUTH` fix names them.
- **Served over MCP.** It changes a field value and deletes nothing, so it is an ordinary write: `writes: true`, `--allow-write`, the connection's `writes` setting. Not a breaking change (principle 7): an additive command, so no contract entry or divergence was needed.
- **Verified only against fixtures.** The queries and the mutation follow the GraphQL reference; the fixture's answers are invented from it, not captured from a live project. `suspected-bug` and live verification are for the first run against a real board.
- **Toil UI.** `proposeMove` for a GitHub item that is on a board proposes `github project status --item <id> --to <status>`, the status word taken from other items in that column as for Jira and Azure DevOps. With no board item or no peer status the proposal says so and keeps a hint that lists the options (`github project fields`).
