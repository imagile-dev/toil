# Toil UI reads every repository and project a dossier names (#542)

- **Built the full version, not only the header.** Each repository gets the same reads the single one did (issue list or board issues, histories, `pr list`, `pr get`, CODEOWNERS), so the board, PRs and People views see all of them. Why: the loader already ran per-repo reads behind one `owner/repo`, so looping them was smaller than a header that explained why they were missing. The header half is kept too: `DossierData.githubRepos` says which repositories were read, and a repository whose issues or pull requests failed gets a line on the Pull requests view (beside the failed call on its panel), not a silent gap.
- **One source of truth for the repository list**, `ui/src/github-repos.ts`, from the dossier as `dossiers show` returns it: the resolved `owner`/`repo`, the `github` section's plain or per-repo values, then `repos` remotes. Deduplicated without regard to case. It does not call `repos scan` or look at the working folder.
- **A remote counts as GitHub's if its host is github.com or the host of a remote whose owner/repo the section already names.** Remotes carry no service label, and the UI has no connection host to compare. This avoids reading a Bitbucket or Azure DevOps remote as GitHub. A dossier with a GitHub Enterprise host and no github owner/repo gets no remote-derived repositories, which is the safe direction. A remote on github.com with an enterprise connection fails loudly on its panel rather than being skipped.
- **`owner` and `repo` are passed on every GitHub call**, never left to toil's dossier or git-remote resolution, so the UI keeps working when core stops falling back silently for a per-repo dossier (#540). When no repository can be worked out, one unscoped call goes as before and its failure shows.
- **The closed-history caps are per repository** (`CLOSED_ISSUE_HISTORIES` 50, `CHECKED_CLOSED_PRS` 20), because each repository's list is its own call and a shared cap would let one busy repository starve the others of histories. Cost: first-sync request volume scales with the repository count (up to 50 + open histories and 20 + open PR gets each). `PER_ITEM_CONCURRENCY` bounds the whole dossier at four at once: each repository's issue list goes through the same pool as the per-item reads (the PR lists run one repository after another).
- **Issue histories are keyed `owner/repo#n`** when handed to `mapOwi`, so two repositories' issue 12 never join the wrong item.
- **A project board is read once per project**, under the section's plain owner (the first repository's when owner is per repo), and each repository takes the issues of it that live there (matched case-insensitively on `nameWithOwner`). Items on the board from repositories the dossier doesn't cover are still ignored, as before.
- **The sample dossier's GitHub calls now carry `owner` and `repo`** in the fixture; no multi-repo sample was added (its data is shaped by test fixtures from the main package, and the unit test builds a second repository from the first by renaming it).
- **Not done:** repositories are not shown as a chip on the board cards (that is #541's card work) and the dossier header itself is unchanged; the read/not-read list is on the data and the Pull requests view only, to keep the screens quiet.
- **Scope widened to Jira, Bitbucket and Azure DevOps** (maintainer's call), because #540 stops a per-repo value that matched no repo falling through to git or the connection, and Toil UI sends only `dossier`. `ui/src/targets.ts` turns a section's context inputs into targets: plain values are one target that names nothing (the calls go out as they always did), and a per-repo map is one target per repo name, carrying the section's plain values too, de-duplicated (two repos in one project are one project). A repo name missing one of the section's keys is skipped.
- **What is read per target:** Jira, one search per distinct `project` (history calls follow their issue); Azure DevOps, the work item reads once per distinct `collection`/`project`, pull requests once per `project`/`repo`, and each pipeline is asked of the projects in turn and kept from the first that has it (a failure is recorded only when none does); Bitbucket, `pr list` and `pr get` once per `project`/`workspace`/`repo`. Item and change ids already carry the project or repo, so they stay unique. The `ado` work item mapping is the one thing not exercised with two projects of real data.
- **No remote-derived targets outside GitHub.** Bitbucket and Azure DevOps remotes are parsed by core against the connection's base URL, which the UI doesn't have; inventing host heuristics for them was ruled out. A dossier that relies on a remote for those areas is read as toil resolves it.
- **Jenkins jobs are still tried against every Bitbucket pull request,** as before: a job names no repo, so the UI can't tell which repo's PRs a job builds. Two repos with the same PR number could be matched to one job's run. Left as is.
- **`DossierData.githubRepos` became `readTargets`** (`{ area, label, work, pullRequests }`), one entry per place read, in every area. Each entry that failed gets one muted line where its gap appears: `pull requests not read` on the Pull requests view, `work items not read` on the Board tab (plain text), and the panels keep the failed call.
- **A pipeline is tried in each Azure DevOps project in turn** and kept from the first that answers, because it lives in one project and the others would answer "not found" and put false errors on the Builds and Deployments panels. Only when no project has it is a failure recorded (the last one's). With one project the behaviour is unchanged.
- **A repo name a section leaves half-named** (a `repo` entry with no `project` entry, say) is no longer dropped silently: Bitbucket and Azure DevOps record it as a place whose work items and pull requests were not read, so it gets the usual muted lines.
