# Toil UI's sync for large projects (#493)

- **The window is the cache's retention period.** Jira reads `project = X AND (statusCategory != Done OR updated >= -Nd)`, Azure DevOps the same on `ClosedDate` and `ChangedDate`, with N the cache's `retentionDays`, because the cache prunes anything older anyway. The sync passes it as `windowDays`; a browser that doesn't says `DEFAULT_WINDOW_DAYS` (30, the cache's default).
- **The cache answers the dashboard's search whatever window it names.** The browser doesn't know the retention, so a sync with `--retention-days 7` stores a different query text than the browser sends. `isDashboardQuery` recognises the loader's own JQL or WIQL, and the store then answers with the stored search of that command. An agent's own JQL never matches, so it is never answered with a search it didn't ask for.
- **Azure DevOps "open" is an empty `Microsoft.VSTS.Common.ClosedDate`.** WIQL has no status category. The Agile, Scrum and CMMI processes set that field on reaching a closed state; an item that is closed without it (a Removed item, a custom process) counts as open and is read every time. `toil ado work-item search --updated-since` parenthesizes the WHERE it is given, so the clause composes (unit-tested against both areas' `andWhere`). Not verified against a live server.
- **Reconcile once a day (`RECONCILE_MS`, 24 hours).** A search "since" can't see a deletion or a move, so once a day, and on the first sync after the upgrade, the search is also sent whole: Jira with `fields: key`, WIQL as it is (ids already), `github issue list` plain. Cached items it doesn't list are dropped. A failed reconcile call fails the source like any other call, keeping the last good copy and the old watermark. The last whole listing is `sources.full_read_at` (schema 5), set only when every search of the source was whole.
- **Because the window is part of the whole listing, an item that has been closed longer than the window leaves the dashboard at the next reconcile**, not only at retention. That matches what the cache would have pruned.
- **Unchanged rows are written lazily.** A response is compared by a SHA-256 digest of its answer (ok, data, error, warnings, context; not how long the call took), so a response the sync reused isn't even compared. Items, transitions, change refs and worklog facts are compared by their JSON text. A row nothing changed is refreshed to the sync's time only when it is more than a quarter of the retention period old, in one UPDATE per table, so the rows are written about four times per retention period instead of every sync, and are never older than it. Worklog facts follow the same rule; their content and the news they produce are as before.
- **The STALE warning names the source's last successful sync**, not the row's `synced_at`, which the lazy refresh makes less exact.
- **Concurrency is 6 (`PER_ITEM_CONCURRENCY`) across a whole dossier, not per area.** One shared gate for histories and pull request gets, so a dossier with Jira, GitHub and Azure DevOps doesn't open 18. Results and the recorded calls come back in the order of the ids. toil retries a 429 itself. The job's counters are plain increments on one thread, so they stay correct.
- **Not changed:** the GitHub board, Azure DevOps iterations, builds and deployments are still read whole (the issue's third bullet; they are bounded already or need toil). The loader still maps every item through OWI on a no-change sync; only the local writes are incremental.
- **The simulation lives in `ui/test/scale-sim.ts`** and runs in the suite (about a second). Before and after numbers for 3000 items, 200 live: first Jira sync 3045 calls became 217, first Azure DevOps sync 3011 became 211, and a no-change sync writes 9 rows instead of 18068 (Jira) and 3 instead of 9038 (Azure DevOps).
