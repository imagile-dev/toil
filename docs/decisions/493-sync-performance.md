# Toil UI's sync for large projects (#493)

- **The window is the retention period with a six-week floor (the maintainer's call, 2026-10-27).** Jira reads `project = X AND (statusCategory != Done OR updated >= -Nd)`, Azure DevOps the same on `ClosedDate` and `ChangedDate`, with `N = max(retentionDays, LOOKBACK_DAYS)`. `LOOKBACK_DAYS` is 42, derived from `THROUGHPUT_WEEKS` (6) in `ui/src/model/flow.ts`, so the throughput chart's look-back and the read window can't drift. The sync passes `windowFor(retentionDays)`; a browser that doesn't says `DEFAULT_WINDOW_DAYS`, the floor applied to the default retention (30), so 42. The cache prunes by when a row was last synced, not by when an item changed, so the window is a choice, not something the cache forces: a closed item older than it isn't read and leaves every view, and the floor keeps the longest view (6-week throughput) whole.
- **The cache answers the dashboard's search whatever window the browser names, and only that.** The browser doesn't know the retention, so a sync with `--retention-days 7` stores a different query text than the browser sends. `withWindow` rewrites only the window of the dashboard's own JQL or WIQL to `windowFor(cache.retentionDays)` and the store then looks the result up exactly. Any other difference (another project, another clause) is NOT_FOUND. The first version fell back to the newest stored search of the command and answered one project's query with another project's; it was dropped. Agent tools call toil live, not through the store.
- **Azure DevOps "open" is an empty `Microsoft.VSTS.Common.ClosedDate`.** WIQL has no status category. The Agile, Scrum and CMMI processes set that field on reaching a closed state; an item that is closed without it (a custom process) counts as open and is read every time. `toil ado work-item search --updated-since` parenthesizes the WHERE it is given, so the clause composes (unit-tested against both areas' `andWhere`). **Verified live** against an Azure DevOps Services project: the windowed WIQL was accepted, composed with `--updated-since`, and `[Microsoft.VSTS.Common.ClosedDate] = ''` selected exactly the 38 items not in a done state (New, In Progress, Committed, To Do, Approved, plus 2 Removed), while 8 were closed. Azure DevOps Server is not verified.
- **Reconcile once a day (`RECONCILE_MS`, 24 hours), for Jira and Azure DevOps only.** A search "since" can't see a deletion or a move, so once a day, and on the first sync after the upgrade, the search is also sent whole: Jira with `fields: key`, WIQL as it is (ids already). Cached items it doesn't list are dropped. `github issue list` is left out (`reconcile: false`): it has no window, so a whole listing would read every issue the repository ever had, every day. The last whole listing is `sources.full_read_at` (schema 5), set only when every search of the source was whole. The progress line "listed whole: N no longer there" is said only when N > 0.
- **A failing reconcile doesn't freeze the source.** The delta's merged results are kept, the watermark moves on as for any delta sync, the failure is said in the job's messages, and `full_read_at` stays where it was, so the next sync lists the source whole again. I did not mark the source failed: the reconcile only prunes deletions, so the data is as good as a normal delta sync's, and a failed source would show stale data on screen for what is only a missed clean-up.
- **Items closed longer than the window leave the dashboard at the next reconcile**, not only at retention.
- **Unchanged rows are written lazily.** A response is compared by a SHA-256 digest of its answer (ok, data, error, warnings, context; not how long the call took), so a response the sync reused isn't even compared. Items, transitions, change refs and worklog facts are compared by their JSON text. A row nothing changed is refreshed to the sync's time only when it is more than a quarter of the retention period old, in one UPDATE per table, so the rows are written about four times per retention period instead of every sync. Expiry doesn't read that date (next entry).
- **A lazily refreshed `synced_at` means "last confirmed within retention/4"**, so no view should display it, and prune doesn't use it. It prunes responses, items, transitions, change refs and worklog facts per dossier with the plain cutoff, by `dossiers.last_sync_at` (set by every sync and every failed `dossiers show`): once a dossier hasn't synced for `retention` days, all five go together, none half-present, and no row outlives the period `--retention-days` promises. A sync already deletes rows that are gone and touches a failed source's rows, so per-row expiry only matters once a dossier stops syncing. Rows with no dossier row go too. Worklog facts also get a per-row rule, because a fact is only upserted and one no sync produces any more (its item left the sync) would live as long as the dossier syncs: they go when their `synced_at` is older than 1.25 x retention. A fact a sync still produces is refreshed whenever it is over retention/4 old, so while its dossier survives its `synced_at` is within 1.25 x retention and the rule never splits a live dossier's facts; facts nothing produces go about 1.25 x retention after they were last seen.
- **The STALE warning names the source's last successful sync**, not the row's `synced_at`, which the lazy refresh makes less exact.
- **Concurrency is 4 (`PER_ITEM_CONCURRENCY`; the maintainer's call, 2026-10-27) across a whole dossier, not per area.** One shared gate for histories and pull request gets, so a dossier with Jira, GitHub and Azure DevOps doesn't open 12. Results and the recorded calls come back in the order of the ids. toil retries a 429 itself. The job's counters are plain increments on one thread, so they stay correct.
- **Not changed:** the GitHub board, Azure DevOps iterations, builds and deployments are still read whole (the issue's third bullet; they are bounded already or need toil). The loader still maps every item through OWI on a no-change sync; only the local writes are incremental.
- **The simulation lives in `ui/test/scale-sim.ts`** and runs in the suite (about a second). Numbers for 3000 items, 200 live, with the 42-day floor and 4 at a time are in the PR.
