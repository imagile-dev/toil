# One CLI and MCP surface per product: Jira Data Center and Cloud (#495, slice 1)

The maintainer's decisions on #495 (2026-10-27) are not repeated here: one area per product with a `deployment` on the connection, config version 3, the old names removed with no deprecation period, the union surface with a clear refusal, and variant-native `data`. These are the defaults this slice chose within them.

- **The refusal is `UNSUPPORTED`, which already existed, not a new `NOT_SUPPORTED`.** Its meaning ("the server doesn't have what the command needs") already covers a deployment that has no such command or flag, and one more code for a near-identical situation would leave a caller choosing between two. Its documented meaning in `src/core/errors.ts` and `audit stats` is widened to say so; no existing use changes. It is raised after the connection resolves and before the write gate, so a missing command is never reported as a missing opt-in. The message names the flag on the CLI and the field over MCP, and the fix names the user's connections that can run the call.
- **`deployment` is `server` or `cloud`, defaulting to `server`.** The names are the vendors' own words for the two products (Server/Data Center, Cloud), `server` being the contract's. It has a zod default and an area `defaults` entry, so `connections add` offers `server` and writes nothing for it. Cloud's `email` is optional in the schema and required by the existing `variants` mechanism, so the usual "Cloud connections need email" fix appears. Its labels are "Data Center" and "Cloud", which the refusals and help text use.
- **Migration folds `defaults.jira-cloud` carefully, because `defaults.jira` reaches every Jira connection.** The connection default folds as asked (jira's wins, with a `CONFIG_DEFAULT_KEPT` warning naming the one set aside). A Cloud default for another key (`project`) moves to `defaults.jira` only when no Data Center connection would inherit it; otherwise it is written onto the Cloud connections themselves. And a `defaults.jira` that named no connection keeps meaning what `toil jira` used before (the connection called `jira`, else the only one), since folding must not turn a Data Center user's default into their Cloud connection. Keychain references are untouched. The step runs for version 1 and 2 files only; a version 3 file that still says `jira-cloud` is a `CONFIG_RENAMED_AREA` warning with the new form.
- **`TOIL_JIRA_CLOUD_*` and `TOIL_CONN_<NAME>_AREA=jira-cloud` are `CONFIG_INVALID`, not a warning.** A warning rides in `meta.warnings`, where the one person whose pipeline it was is the likeliest to miss it, and the variable carries a credential that would otherwise be dropped in silence. The cost is that every command that loads config fails until the variable is renamed, which is the loud failure principle 4 asks for. `src/core/renamed-areas.ts` is the one table the env check, the config warning, the dossier fold, `--areas` and the typed-path error all read, so the next fold (`confluence-cloud`) is one line.
- **`toil jira-cloud …` is an `INVALID_INPUT` naming the new form,** raised where commander reports an unknown command, so it works for any depth of path. `--areas jira-cloud` is `INVALID_INPUT` too, ahead of the unknown-area check.
- **Dossier `jira-cloud` sections (top level, per environment, and `people[].ids`) are read as `jira`,** with a `DOSSIER_RENAMED_AREA` warning by key path; with both present `jira` wins and the warning says `jira-cloud` is ignored. Because a dossier has one `jira` section, it picks one connection: a dossier can no longer name a Data Center and a Cloud Jira at once. That was possible with two sections and is the cost of one area, flagged for the maintainer.
- **The core helper is `area.byDeployment({ server: [...], cloud: [...] })`, not `routed`,** because `routed` already means a routed alias (`deps frisk --source`). It folds finished `area.command()`s, one list per deployment, rather than taking a spec per command: each deployment's files stay as they were (move, rename, `jiraArea`), and nothing about a command's own examples, run or schema is rewritten. The folded command's `deployments` records, per deployment, the fields its implementation takes and its `run`; `exampleDeployments` tags each example.
- **The union input takes the first deployment's schema where the two declare a field differently, and each implementation re-validates its own call.** `issue search --limit` is a number-or-text on Data Center (the recorded `parseInt` reading) and a positive integer on Cloud; `key` is any string on Data Center and non-empty on Cloud. The union uses Data Center's (the looser, the contract's) and Cloud's own schema still runs, text read as typed the way argv is (`fromText`), so Cloud's refusals and messages are what they were. A field only one deployment takes, or that only one requires, is optional in the union and enforced by the one that requires it. Cloud's `log-work --started` is the case in point. Descriptions and flag spellings that differ must be reconciled in the area's `overrides.ts`, or the registry refuses to build; that list is the price of one honest help text.
- **`jira issue schema` is hand-written, not folded.** It needs no connection, so there is no deployment to route by; it takes `--deployment <server|cloud>` (Data Center by default, the recorded behavior). A routed definition of a connectionless command throws.
- **`queryByPost` is the OR of the two.** Cloud's `issue get` of several keys is a POST read, Data Center's is not; the property only widens what the parity suite lets a read send.
- **Fixtures: `AreaFixture.deployments` names the connection per deployment, and `examplesOf` adds it to each example.** The fixture's `config` keys are connection names, and an entry may set its own `area`; the area's default is the connection named after it, so `jira` stays the default and Cloud is `jira-cloud`. Cloud's canned responses moved to `test/fixtures/jira-cloud-data.ts` (not a fixture, and not discovered as one), with routes pinned to the Cloud origin so the two sets of agile paths cannot answer each other. Cloud's two input files were renamed `cloud-issue.json` and `cloud-update.json` because the merged fixture serves both sets of files from one folder. The suite was broken on purpose twice (every example on the Data Center connection; dispatch hard-coded to Data Center) and failed 25 and 81 tests, then passed again. New parity cases prove the refusals through both doors with no request sent.
- **The contract records Data Center and stays as it was; Cloud is additive.** No `command-contract.json` entries were added: `project list`, `project get`, `user search` and `issue schema --deployment` are commands and a flag the contract does not have, which the contract test allows. The one spelling that differs from a recorded flag, `--assignee <user>` (it was `<username>`), is a divergence under principle 10. `CONTRACT_VERSION` is 2, with a history table in `docs/command-contract.md`. The contract's output-field test runs only Data Center's examples, since Cloud returns its own API's shape by decision.
- **The site and skill have one page for Jira with one verification level (`unit`).** The site's integration data holds a single `status` per area and both deployments are `unit`; if one is raised alone later, the data model needs a per-deployment level first. `jiraSupported` keeps Data Center's floor (8.14) and says in its note that Cloud is always current. `skills/toil/jira-cloud.md`, the site's `jira-cloud` data files and the `jira-cloud` OWI source are gone.
- **Confluence's shared token respects the deployment.** `confluence-cloud` shared its `apiToken` with `jira-cloud`'s default connection's env value, and `confluence` with `jira`'s. With one `jira` area both would read the same default connection, so a Data Center PAT could be sent to Atlassian's cloud by the env fallback. `shares.fallbackWhen` (new, optional) lets an area say which of the other area's connections may lend: `confluence` takes from a Data Center Jira, `confluence-cloud` from a Cloud one. An explicit `apiTokenFrom` is the user's call and is not asked. This is slice 2's problem too; it is solved here because this slice created it.
- **OWI gains an additive `source.deployment`.** A Jira Cloud item is `source.area: jira` now, so nothing in the item said it came from Cloud, and Toil UI needs that (the sub-task type is `Sub-task` on Data Center and `Subtask` on Cloud). `util owi map` reads it from the envelope's `meta.context.connection.deployment`, the schema and spec say so, and an input that does not say leaves it out. OWI ids (`<connection>:<key>`) do not change.
- **`meta.context.connection.deployment` is reported only for an area whose `variants` are keyed on `deployment`,** so no other area's `meta.context` changes.
- **The game save is not extended to version 2 files.** `src/welcome/rogue/save.ts` saves only to a current-version file and says an older one is not rewritten for a game; that now includes version 2. Rewriting it would migrate it, which the game's "touches nothing else" rule rules out, and any command that saves a connection upgrades the file. The tests use `CONFIG_VERSION`.
- **Toil UI reads one Jira section.** `JIRA_AREAS` is `['jira']`, its command lists lose the Cloud names, and the Cloud-variant dossier test was dropped, since its point (the other area's commands) is gone; the sub-task and proposal tests cover the Cloud item by `source.deployment` instead.
- **`multi-user` stays in the shared custom-field `type` list.** Data Center refuses it when a `--field` is shaped, with `INVALID_INPUT` saying it is a Cloud type, rather than treating it as a raw string.
- **Left for the later slices:** `confluence-cloud`, `bitbucket-cloud` and `ado-cloud` are untouched areas; the integrations skill says so. No Windows, macOS or Node 26 run was made for this slice; CI's platform workflow covers them.
