# Workflow pages in the toil skill (#527, #528, #529)

- **Pages live in `skills/toil/workflows/`, a subfolder, and the bundle keeps the path.** `scripts/gen-areas.mjs` now embeds every Markdown file under the skill, so `skillFiles` has keys like `workflows/review.md` and `skillPages` keys like `workflows/review`. `writeBundledSkill` creates the folder when it installs. The alternative, flat names such as `workflow-review.md`, would have needed no code change but would put job pages beside the area files that `test/skills.test.ts` holds to the area rule. Applies to the bundle, `toil skill install`, the site and MCP.
- **The frontmatter is single-line `key: value`, with JSON for `needs`, `inputs` and `writes`.** The skill's other frontmatter readers (`bundled.ts`, the site, `test/skills.test.ts`) all read one line per key, and JSON is valid YAML flow syntax, so Toil UI (#532) can parse it with either. `needs` is `{ all, any, optional }`, so alternatives are `any`. `inputs` is `[{ name, dossier }]`. `loop` is a round count or `none`. `verification` is `unit` or `live`.
- **A workflow page's description has no ": ".** The site compiles each file's frontmatter as real YAML, where a colon and a space turns the description into a mapping and fails the build, which the one-line readers forgive. The suite parses every workflow file with a YAML loader and holds it to the one-line reader.
- **`writes` holds full command paths (`github pr comment-inline`), one per host.** A bare `pr comment-inline` would be shorter but leaves Toil UI to guess which host's write it means. The suite checks each entry is a write command in a `needs` area, that the page shows it, and that no write command the page shows is missing from the list.
- **A `toil <host> …` line stands for every host in `needs.any` and is checked once per host.** A verb one host lacks (`pr threads` on Bitbucket) then fails the suite and goes in the page's per-host table, so a host-neutral line can't quietly be wrong on one host.
- **Waiting on GitHub checks uses `commit checks`, not `pr status`.** `pr status`'s counts treat GraphQL's uppercase states as `other` (suspected bug #72 item 1, still pinned by a test), so a wait on `checks.pending` would end at once. The wait expression is `length(@) > to_number('0') && length([?status != 'completed']) < to_number('1')`, with `--select` before `wait`. Checked against a real merged PR. For Bitbucket and Azure DevOps the page tells the agent to read `pr builds` once and wait on the state field it shows, because the page can't state a field name it hasn't seen live.
- **Round counting is a comment on the PR starting `Round <n> of 3`.** There is no host field for a round, and a comment is visible to the person. On GitHub the count is a `--select` over `pr comments`; on the other hosts the agent counts the same way over the text field.
- **`needs-human` is a label only on GitHub (`issue label`).** Bitbucket and Azure DevOps have no label command, so the page posts a `needs-human` comment saying what is left. A label command for them is a separate change.
- **Commit, push and `git diff --name-only <commit>` stay the agent's own git.** toil's `git` area is read-only and has no range diff, and the README names them as the one exception to "only toil". Reviewing and shipping can't be written without a push.
- **The C4 model has no provenance field, so an inferred element's `description` starts with `(inferred)`.** #529 asks the diagram to draw observed and inferred differently. `util c4` takes no such field today; a field is a change to that command, not to this page. The map file carries `how: observed|inferred` with a `source` or `reason`.
- **The map file is read with the agent's own tools, not `--select`.** `--select` works on a toil command's output, and no command reads a JSON file back. The page says so rather than promise it. A command that does is a separate change.
- **`git log` lists no files, so hot spots from it are marked inferred.** The page reads them from commit-message scopes. Per-file churn would need `git log` to return file names.
- **Import edges come from `util size`'s `outline.imports`** (#529's primitive, its own PR, merged first). The page says they are syntactic and unresolved, and falls back to manifests and folders for a language with no outline.
- **SKILL.md stays under its 4 KB cap by tightening other lines.** It was 4,089 bytes before the By job block and the longer description, so a few sentences in "Every call" and the file table were shortened without dropping a safeguard: the Feedback line keeps "to that exact report". The By job block is a heading, one sentence and three lines.
- **The description names the jobs in both places.** SKILL.md's frontmatter and the description `bundled.ts` generates both end with "Also use for whole jobs such as review this PR, ship this branch, or map this codebase." The generated one keeps its existing rule of naming only areas and engines from config, and its check that every name is lowercase letters, digits and hyphens, since the jobs sentence is fixed text.
- **MCP serves the workflow pages whatever `--areas` says.** `toil://skill/workflows/<job>` and `toil://skill/workflows/README` are listed like `upgrading` and `changelog`: a job spans areas, and an MCP-only agent has no folder to read. The cost is four more listed resources.
- **The site renders the pages from the files.** `/docs/workflows/` is the README plus a generated list of jobs, and `/docs/workflows/<job>/` is each page, both through `SkillPage`. The docs path gains one "Workflows" link under Agents. A job page is off the pager walk, as `/connect/` pages are.
- **Every page says `verification: unit`.** None has been run end to end with the run recorded, as #526 requires for `live`. The reads of `review.md` were run against a real merged PR and recorded in the PR.
