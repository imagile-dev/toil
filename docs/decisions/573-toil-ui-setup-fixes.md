# Toil UI setup fixes (#573)

- **The wizard asks for the Jira project key, optionally.** Label "Jira project key (optional)", hint "The letters before the number in an issue key, such as PAY in PAY-123." When it is left empty the hint adds "Leave it empty and Toil UI reads no Jira issues, unless the Toil project already names a Jira project." It sits on the Toil project step of the setup wizard and on the tools page of New Toil project, only while a Jira link is ticked, and goes to `projects link` as `--set project=KEY` on the Jira link only (`withJiraKey`, `ui/src/views/project-create.ts`). It is hidden when the Toil project chosen was already linked on an earlier visit, since nothing would send it.
- **Find the fields saves the key it sampled from, only where the Toil project names none.** `projects link <toil-project> jira --set project=KEY`, never `--replace`, run after the field names and shown in the results as "Jira project key". "Names none" means `projects show` was read and had no Jira project; if that read failed the key is not saved, since unknown is not none (principle 12). The note says so before the button is pressed.
- **Sync asks Jira search for a list of fields, and reads the connection's registered fields first.** `jira issue fields` (no `discover`, so no request to Jira) runs before the searches, and its answer is a source of the `jira` area like the searches (`READ_COMMANDS` gains it). `fields` is the standard search fields, `description`, `resolution`, `resolutiondate`, `duedate`, `parent`, `subtasks`, `issuelinks` (everything `mapOwi` reads that search leaves out), every registered custom field id, and the field each of the Toil project's `estimate`, `iteration`, `team`, `dueDate`, `priority` and `type` names. I added `acceptanceCriteria` to those because the readiness check reads it from the issue the same way. `description` is included because readiness's description check reads the body and a search without it showed every Jira item as having none.
- **A name search would refuse is left out of `fields`.** A name that is not registered and has whitespace makes the whole search `INVALID_INPUT`; leaving it out lets `mapOwi` report the field as missing instead.
- **An override that names a registered field by id is rewritten to its registered name before `mapOwi`.** Search returns a registered field under its name, and `mapOwi` looks the override up by key. The OWI key meanings are unchanged.
- **Where the standard list lives.** `src/areas/jira/{cloud,server}/client.ts` import node-only code, so the page copies `STANDARD_SEARCH_FIELDS` into `JIRA_STANDARD_FIELDS` (`ui/src/load.ts`), and `ui/test/config.test.ts` holds it to both.
- **Changing a search's input is a re-read, once.** The cache keys a stored search by its input, so the first sync after this ships has no stored copy of the new search and lists the project whole, as a changed registered field would.
- **The summary has two lines.** "Couldn't check." is a lens that did not run (no work-in-progress limit, no sprint running), "Partly checked." a lens that ran but could not test some items (for instance in-progress items with no assignee). Each keeps its notes in its own fold. The split follows `lens.checked` from `src/core/brief/brief.ts`, which is unchanged. `BriefingView` gains `partlyChecked` beside `unchecked`.
- **A connection can take no secret, and is "not needed", not "missing".** `TokenState` gains `none`, worded "not needed" in the guide's context and beside a connection in the wizard (which also stops offering to replace a token that does not exist). `connections list` does not say which engine a database connection uses, so `secretKeysFor` works out the possible variants from the settings the connection holds (a variant is possible when every setting it requires is set), and drops a secret that `appliesTo` names only other variants. When it cannot tell, every secret counts, so "not needed" is only said when it is certain.
- **The `db` area now declares which engines take each secret** (`src/areas/db/index.ts`: `appliesTo` for `password` and `token`). The registry did not say, because a database's `requires` names settings, never secrets. This is registry metadata; the one place it reaches beyond Toil UI is that the connection form treats a field that does not apply to the chosen engine as hidden, so adding a SQLite connection no longer offers a password. Flagged for review as a change outside `ui/`.
