# One CLI and MCP surface per product: Bitbucket Data Center and Cloud (#495, slice 3)

The maintainer's decisions on #495 and the Jira slice's defaults (`docs/decisions/495-unify-jira-deployments.md`) apply unchanged: a config fold with `"deployment": "cloud"` on the connection, the old names removed now and failing loudly, a union surface with `UNSUPPORTED`, variant-native `data`, an empty retired env var ignored unless `TOIL_STRICT_ENV=true`, one dossier section per product, every save writing config v3, and a stale `TOIL_<AREA>_*` on a Cloud default refused unless `TOIL_<AREA>_DEPLOYMENT` is set. `bitbucket-cloud` is one more line in `RENAMED_AREAS`, which carries all of that. These are the defaults this slice chose within them.

- **`--project` and `--ws` are different ideas, so both stay and each is refused on the other deployment.** A Data Center project is the container of repositories. A Cloud workspace is the account that owns them, and Cloud has projects too, inside a workspace, which no command here uses except `repo create`. Folding `--ws` into `--project` would have been a flag that means two things. The refusal is `UNSUPPORTED` naming the flag and the deployments that take it, before any request, and the help text of each flag says which deployment it is for. The contract's group flags `--project <key>` and `--repo <slug>` are unchanged; `--ws <slug>` is the spelling Cloud already had (toil's own `--workspace` is the file-workspace flag).
- **Core: `ContextInput.deployments`.** A context input can name the deployments that take it (`project: ['server']`, `workspace: ['cloud']`), and `ContextInput.missing` can be a function of the resolved connection, so each deployment's missing-input message keeps its own words ("Could not determine Bitbucket project/repo" on Data Center, "No Bitbucket Cloud workspace given" on Cloud). The folded command's `deployments.routes` now carry the context each implementation needs, `resolveCall` resolves and requires only the route's own inputs for the connection's deployment, and a call the deployment is about to refuse (`--ws` on Data Center) is told so rather than told what Data Center's inputs lack (`refusesDeployment`, asked before the missing-input error). `byDeployment` no longer demands that both implementations declare identical `context`; it unions them. `area.command()` records which inputs a command listed itself (`contextListed`), because the area's group-level inputs reach every command: that is how a deployment takes an input the area gives the other one on one command only.
- **Cloud's `repo create --project` is now the shared `project` context input, not a field of its own.** Before, it was an optional `--project <key>` on one command. The merged `repo create` has Data Center's required `--project` already, and they are the same idea (the project the repository is created in), so one flag. On Cloud it is optional and listed by that command alone (`contextListed`); every other Cloud command refuses `--project`. It also now resolves from a dossier and from the connection's `project` setting like any context input. The request it sends is unchanged.
- **`--reviewers` is one flag, `--reviewers <users>`, the contract's spelling.** Its help says usernames on Data Center and account ids (or `{uuid}`s) on Cloud. The placeholder is the contract's, so no divergence is needed; it was `<ids>` on Cloud.
- **`pr diff`'s id is optional in the union (`[id]`), and Data Center still requires it.** Cloud diffs a commit spec (`--spec`) instead of a pull request, so the argument cannot be required for both. A Data Center call without one is `INVALID_INPUT`, naming the missing id, before any request (the Data Center implementation's own schema runs on the call). The fold merges positional arguments that differ only in `required` and takes the optional one. The contract records `<id>`, so this is a divergence in `docs/divergences/bitbucket.json` (principle 10).
- **`pr needs-work` and `pr request-changes` are one command.** Data Center's `needs-work` (the contract's name) and Cloud's `request-changes` are the same idea under two names, so the folded command is `pr needs-work` and `request-changes` is a CLI alias of it on both deployments. The MCP tool is `bitbucket_pr_needs_work` only, since aliases are CLI only, so a former `bitbucket_cloud_pr_request_changes` caller moves to that name. Aliases are now the union of both implementations' (Data Center's `git current-pr` is kept for `pr current`, which Cloud never had).
- **`pr current` is `connectionOptional` for both.** Data Center's answers "Requires Bitbucket config" when there is no connection at all; Cloud had no such behavior. With no connection there is no deployment to ask, so the first deployment (Data Center) answers; with a connection, its deployment does. `byDeployment` takes the OR of `connectionOptional`.
- **Git remotes stay Data Center's.** `parseBitbucketRemote` accepts `bitbucket.org` for a Cloud connection by accident (its host check is a substring match on `api.bitbucket.org`), and would have started deriving a Cloud connection's `repo` from a remote, which Cloud never did and the skill said it did not. The `project` and `repo` readers return nothing for a Cloud connection, so nothing about Cloud context resolution changes. Reading a Cloud workspace and repository from a `bitbucket.org` remote is a later, additive feature.
- **The Pipelines fallbacks apply to a Cloud default only.** `BITBUCKET_WORKSPACE` and `BITBUCKET_REPO_SLUG` were `bitbucket-cloud`'s CI fallbacks and are canonical for Cloud alone (Configuration Precedence 3), so the area declares them with `fallbackWhen: (effective) => effective.deployment === 'cloud'` (core, `defineArea`): the condition reads the default connection's effective settings, and a Data Center default keeps the repo its file says. A pipeline that used Cloud must set `TOIL_BITBUCKET_DEPLOYMENT=cloud`; the skill page says so under "Moving from `bitbucket-cloud`".
- **`pat` is optional in the schema and required for Data Center by `variants`.** The connection has to hold both deployments' credentials. Cloud's either-or (an access token, or an email with an API token, never both) stays in the request hook as it was, with the same errors, because `variants.requires` cannot say "one of". `deployment` defaults to `server`, so a Data Center connection written before the fold needs nothing added.
- **Onboarding a `bitbucket.org` host offers `deployment: cloud`.** The area's `siteApis` maps `bitbucket.org` to `https://api.bitbucket.org/2.0`; with one area, `toil dossiers onboard` would have offered that base URL on a connection that defaults to Data Center. For an area with deployments, a host the area names a hosted API for now offers `cloud` too (`suggestedSettings`). The report's `suggest` field is unchanged.
- **`check-dossier` is Data Center's only.** Cloud had none. A Cloud connection gets `UNSUPPORTED`, and the tool description says so. A Cloud check would need a call per workspace and repository and is left for when it is wanted.
- **OWI picks the Bitbucket shape by the connection's deployment.** `bitbucket-cloud` was its own OWI source because its shapes differ in almost every field. The mapper is chosen by `source.deployment` (additive on a Change now, as on a work item), or, for an envelope that carries no deployment, by the shape of the record (a Cloud pull request has a `destination`). OWI ids (`<connection>:<repo>#<n>`) do not change. The spec, schema and the pull request fixture follow.
- **Toil UI reads one Bitbucket section.** `PR_HOSTS` has one `bitbucket` entry; the review proposal reads `source.deployment` (`pr add-reviewer` on Data Center, `pr update --reviewers` on Cloud, which replaces the list and says so). The sample `checkout-web` dossier's Cloud section is a `bitbucket` section that names the Cloud connection, so Toil UI now also reads Jenkins builds for a Cloud dossier that lists jobs, which it could not before; no sample dossier does. The sample catalog's Bitbucket entry and the positional-field table follow the registry, and `pr request-changes` leaves that table with the alias.
- **Fixtures: the Cloud responses moved to `test/fixtures/bitbucket-cloud-data.ts`,** and `bitbucket.fixture.ts` runs both deployments on a connection each (`bitbucket` and `bitbucket-cloud`), with every route pinned to its own origin. Each deployment's unit tests moved under `server/` and `cloud/` and still run their own commands directly. The parity suite's field-coverage check now ignores an input no deployment of a command takes (`--ws` on `pr create-many`). The suite was broken on purpose (see the PR) and failed, then passed again.
- **The contract version stays 2.** `CONTRACT_VERSION` was raised to 2 for the Jira fold, and no toil release contains it yet (the latest tag is `v0.1.0-beta.2`), so one release carries all the slices at 2. `docs/command-contract.md` records the Bitbucket fold in the same row.
- **Left for the later slices:** `ado-cloud` is still an untouched, separate area. No Windows, macOS or Node 26 run was made for this slice; CI's platform workflow covers them. The two `test/stub-area.test.ts` cases and one `ui/test/server.test.ts` case cannot run in this worktree, where `node_modules` is in the parent folder (they spawn `tsc` and read `react-aria` by path under the worktree); they were not changed.
