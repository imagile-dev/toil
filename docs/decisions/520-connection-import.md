# `toil connections import` (#520)

- **The command is `toil connections import --from <tool> [file]`, a preview unless `--save`.** `add` has no save flag (it is a prompt, or `--set`, which saves at once), so `--save` is new here. Preview is the default because an import creates many connections at once, which is a lot to do before anyone has looked.
- **It is `cli-only` with `writesLocal: true`, like `add`, and is not one of the commands `person` may run through `@imagile-dev/toil/api`.** An agent's shell may run it; the skill tells it to run the preview, show the person, and `--save` on their yes, then hand each password over through `connections login` or Toil UI. This is the maintainer's call (2026-10-28), recorded in principle 2. Nothing in it asks a question, so there is nothing for a `person` to answer.
- **A secret is dropped, never carried.** `Candidate` has no password field. A password found in a file, URL or ADO.NET string is reported as a per-connection warning and once in `meta.warnings` (`SECRET_NOT_IMPORTED`). `.pgpass`, DBeaver's `credentials-config.json`, SSMS's encrypted password and any credential store are never read. Every created connection gets `nextSteps`: `connections login <name>` (not for SQLite or Windows authentication), then `connections test <name>`.
- **Writes stay off and no default is chosen.** An import of fifty connections has no "first" that deserves to be the default; a person picks with `connections default`. (`connections add --set` makes the first connection of an area the default; a single connection chosen by name is not the same as the first of a list.)
- **A name that exists is skipped, never overwritten and never suffixed.** Re-running an import is therefore harmless: everything already imported shows up under `exists`. Duplicates inside one batch are suffixed `-2`, `-3`, so that re-running them is stable too. An existing connection with the same engine, host, port and database under another name is flagged (`similarTo`) but the import still proceeds.
- **Names are the tool's folder or server group, then the connection's name, slugged**, plus `--prefix`. Groups are prefixes in every tool; pgAdmin's default `Servers` group and SSMS's root groups are not, since naming everything after the root says nothing. Slugs are cut at 48 characters, start with a letter (`db-` in front of a leading digit) and are checked against the core `CONNECTION_NAME` rule.
- **Every candidate is validated with the real `db` schema before it is previewed**, so the preview never shows what `--save` refuses. The cost: a SQL Server connection with Windows authentication is skipped on macOS and Linux, because the `db` schema's own check refuses it there. It is reported with that reason, not hidden.
- **`--user <name>` exists because three tools keep the login elsewhere.** DBeaver, DataGrip and tnsnames.ora hold no user in the file, and the `db` schema requires one for PostgreSQL, MySQL, SQL Server (SQL login) and Oracle. Without the flag those connections are skipped with a reason that names it. It never overrides a user the file names, and never applies to SQLite, Windows authentication or `nosasl`.
- **Not imported, and said so per connection (principle 4):** SSH tunnels and proxies (importing the host alone would point at the wrong machine), SQL Server named instances (toil connects by host and port; the reason says so), Kerberos and Microsoft Entra sign-in, Oracle SIDs and connect descriptors, Unix sockets and pipes, Teradata (toil needs the Query Service's base URL and system alias, which JDBC settings do not hold), and drivers toil lacks (MongoDB, ClickHouse, Redshift and the like). Custom JDBC driver properties are named in a warning, never silently dropped; their values are not.
- **Default locations are best effort, and a path you name always wins.** DBeaver, Azure Data Studio, VS Code, MySQL Workbench, pg_service.conf, tnsnames.ora and a JetBrains project's `.idea` are well known. SSMS's `RegSrvr.xml` under `%APPDATA%\Microsoft\SQL Server Management Studio\<version>` is searched on Windows, but its path is from Microsoft's documentation and old installs, not from a machine I could look at, so the error also tells you to export a `.regsrvr` (Registered Servers > Export). SSMS's list of recent servers (`SqlStudio.bin`) is binary and not read at all. pgAdmin keeps its servers in a SQLite database, so it has no default file: `servers.json` is an export.
- **The fixtures are shaped from each tool's documentation, not captured from real exports.** Each says so in a comment where the format allows one. Hosts are `*.imagile.dev`, the user is `you`, and every password is plainly fake. A real export of each format is the next check.
- **Limits against hostile files:** 4 MB per file; XML nested at most 64 levels and at most 200,000 elements, walked without recursion; at most 1000 connections per import; a `tnsnames.ora` nested at most 32 parentheses deep; JSON read with `JSON.parse` after comments are stripped, and read through own-property helpers, so a `__proto__` key is an ordinary key.
- **`connections.import` is a documented exception to `files.workspace`** (`docs/bounds.md`, `src/core/bounds.ts`). It still refuses `~/.toil`, the `--config` file, `/proc`, `/sys`, network paths and device paths, compared after realpath. It uses `node:fs` directly, as `connections migrate` does; it spawns nothing and adds no dependency.
- **The XML reader is the `util` kit's tokenizer with a depth and element cap on top** (`src/areas/util/kit/xml.ts`), not a new parser. JSONC is a small comment and trailing-comma stripper in front of `JSON.parse`; there was no JSONC reader in the repository to reuse.
- **A named file may be outside the workspace, and no error quotes its contents.** Exports often sit in Downloads, so the workspace bound would only get in the way; the bounds that remain are the refusals above. Parse errors give the format, the file and a line or position, never the text, since a connection file may hold a password.
- **`--from` names the tool and the file is positional.** `connections` is a core config command, not an integration area, so principle 10's flag rule doesn't bind it. The maintainer may prefer `--format`; it is a rename while this is unreleased.
- **`PGSERVICEFILE`, `PGSYSCONFDIR`, `TNS_ADMIN` and `ORACLE_HOME` are read only to find which file to preview**, matching each tool's own lookup. Nothing else comes from them, and a path given on the command line wins.
- **DataGrip's default `.idea/dataSources.xml` is looked up from the working directory**, since a JetBrains project has no fixed place on the machine.
- **Not done:** DataGrip's `dataSources.local.xml` (where its user names live) is not read alongside `dataSources.xml`; `--user` covers it. DBeaver's extra `data-sources-*.json` files are not read either.
