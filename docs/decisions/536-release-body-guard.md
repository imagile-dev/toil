# A merged release PR that releases nothing now fails loudly, and its body is escaped first (#536)

- The escape is `&amp;lt;`, not `&lt;`. release-please parses the body, re-serialises it from each block's decoded text, and each package's strategy parses it again. `&lt;` decodes back to `<` before the second parse and is a tag again; `&amp;lt;` survives both. Checked with the action's own bundled code. The merged PR's description shows `&lt;` literally on GitHub, which is cosmetic: the GitHub release notes and CHANGELOG read `<NAME>`.
- The escape runs in the workflow, on the release PR's body, rather than by changing commit messages or notes. Any future note can contain `<x>`, and commit bodies come from squash merges that nobody here rewrites. Only `<details>`, `</details>`, `<summary>` and `</summary>` are left alone, since those are the tags release-please reads.
- The escape runs every time release-please opened or updated the PR, and edits it only when the escaped body differs. A cost accepted: release-please updates its PR only when the body it generates differs from the one on GitHub, and an escaped body always differs, so a push to `main` that adds no changelog entry (a `chore:` or `docs:`) now also rewrites the release PR, re-running its dist rebuild and CI. Escaping before release-please writes the body isn't possible from the workflow.
- The escape runs after release-please's job, dist rebuild included, so for a few minutes after each update the release PR's body is unescaped. Merging it in that window is caught by the check below rather than prevented.
- The catch-all check keys on the `autorelease: pending` label of a merged PR after release-please has run: it swaps the label to `autorelease: tagged` in the same run that releases. That catches any cause of a skipped release, not just this one, and fails with the fix. It counts only a PR whose merge commit is in the commit the run built (GitHub's compare API says `identical` or `ahead`): a release PR merged while an earlier push's run was still going is the next run's to release, and would otherwise be a false alarm. It runs even when the escape failed (`!cancelled()`), since the two are independent.
- Every `gh` call sets `GH_REPO`. The guard job checks out only when there is a release PR to escape, and `gh pr list` without a checkout fails with "not a git repository", which on the run that tags a release would have failed the check every time.
- `scripts/release-pr-body.mjs` reads stdin and writes stdout, with `gh` calls in the workflow, so no repo script spawns a process.
- The guard is its own job, `release-guard`, after `release-please`, which no publish job needs. That was the maintainer's call on review (recorded on #536): inside the `release-please` job, a failure in either step skipped the npm publish of a release already tagged in the same run.
