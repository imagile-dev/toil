# Toil UI offers the workflow jobs where they apply (#532)

- **A job is a workflow page; Toil UI keeps no list of jobs.** `ui/src/model/jobs.ts` reads `skills/toil/workflows/*.md` at build time (`import.meta.glob`, `?raw`) and parses each page's frontmatter (`needs`, `inputs`, `writes`, `loop`). Only the face a job wears (Review, Ship, Diagram) is Toil UI's own. Why: the pages are the single source, and Toil UI already releases with the toil whose commands they call, so no change to toil's `./api` (a contract) was needed. Applies to `ui/` only.
- **Running a job is one question to the agent Toil UI already has.** The prompt (`job:<id>:<target>`) carries the page's own steps, the shared rules, and a short statement of what differs in Toil UI (no shell, no working tree, every write a proposal). It runs through the existing Ask path, so every toil call shows in the status line, every write is a card, and the run is kept in the worklog with its citations, as Analyze is. No new endpoint, no new write path. A proposal may name only a command in the page's `writes`.
- **Read tools added for the pages, nothing else.** `LIVE_COMMANDS` gains `pr files`, `pr diff` and (where they exist and never write) `pr threads`, `pr builds`, `pr status` on the three hosts, and `util c4 mermaid` (local, read-only), so Review and Diagram have something to read and draw with. `bitbucket pr comments` was left out: a test forbids a tool name containing "comment", and `pr threads` covers it.
- **Actions sit where they apply, never as a catalog.** Review and Ship are two items in one "Actions" menu per open pull request in Pull Requests (a menu, not a button on every row, principle 11); Diagram is a link on a dossier's overview. All three are in the palette and each has an address: `#/dossier/<name>/job/<review|ship|diagram>?target=<change id or repository>`. The address opens the job's page, which says what it does, what it needs and has the Run button.
- **A missing connection is named, not hidden.** `availability()` asks the pull request's own host for its connection (a GitHub pull request needs a `github` connection, not any of the three), and the menu item stays, dimmed, with "Needs a github connection. Add one in Settings, Connections." under it. Optional areas (`sonar`, `dynatrace`, ...) never block; the page says those steps will be unchecked. When connections can't be read, the job is offered and the run reports it.
- **Ship's loop is counted on the server from the worklog and stops at the limit.** A round is a finished run of that exact question (`Ship <change id>`); stopped and failed runs aren't rounds. Round n of 3 is said above the answer; the run after round 3 is refused with `needs-human` named and what to do, so the stop is shown, not hidden. The page can't count before the first press without a new endpoint, so the round shows when a run starts.
- **Ship in Toil UI is the answer-the-review part only.** Toil UI's agent has no working tree, so editing, running the repository's gate and pushing stay in the person's terminal; the answer says which steps it left. Offered on an open pull request authored by a person (not an agent or a bot), because Toil UI has no notion of "the viewer's own code-host identity". It cannot tell a person's own pull request from a colleague's, and the PR says so.
- **Diagram in Toil UI draws from what the tools return, without a clone.** It has no workspace, so the folder-level steps (`util size`, `git log`, `deps scan`) are reported unchecked, never filled in; the model is built from the dossier's repositories, pull requests, items and deployments and drawn as Mermaid (`util c4 mermaid`) in the answer. Saving the diagram into `docs/` or Confluence stays a proposal or the terminal.
- **The preview's scripted agent answers jobs too**, saying plainly that nothing was read and listing every check as unchecked; its one proposal (`github pr comment`) is held to the registry in `test/registry.test.ts`.
- **A job's proposals may name only the writes its page lists.** The host filters the write commands `finish()` accepts to the page's `writes`; anything else drops like any invalid proposal. The agent also cannot name a file through `util_c4_mermaid` (`file` is a hidden live-tool field), so the model goes in as `text`.
- **Honest failures.** A workflow page that exists but doesn't parse is reported with the reason, not as missing; connections that can't be read are said on the job page ("wasn't checked") rather than swallowed; a missing connection links to Settings, Connections.
- **Open for the maintainer (principle review gaps):** (A) the per-row Actions menu trigger is a control on every open row, chosen for one-press reach, with nothing removed; the alternative is the palette and the job page's own list only. (B) the Diagram link always shows on the overview; the alternative is to keep it in the palette and its address. (C) Ship rounds are finished runs per dossier from the cache, so retention can reset them and the same pull request in two dossiers counts twice; the alternative is reading `needs-human` from the pull request. (D) the prompt says never to merge while Ship's `writes` includes `github pr enable-auto-merge`: it is a proposal a person presses, and the prompt now says "yourself". (E) Ship is offered on any person's pull request. Toil UI parsing the workflow pages' frontmatter is also an interface between the two packages that no principle covers; the same-release rule is what holds it.
- **Not done here:** quick questions stay questions (no page, no job); no job for any candidate page of #526; no pre-run round count in the page.
