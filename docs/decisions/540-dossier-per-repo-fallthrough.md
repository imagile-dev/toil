# A per-repo dossier value never falls through to git or the connection (#540)

- A context input a dossier holds per repo, when the call's folder matches none of the dossier's repos, is `INVALID_INPUT` for a command that needs it (the fix names the dossier's repos, `--cwd`, the flag, and a plain value). Chosen over "resolve nothing from the dossier for the whole key set": that would answer from the connection or git without saying the dossier was skipped, which is the silent wrong answer the issue is about. Applies to the resolver (`src/core/call-context.ts`) through the dossier lookup (`src/core/dossier.ts`).
- A command that merely lists the input as optional (every group-level input is optional on every command) is not refused: the input is left unresolved, taking nothing from git, the connection or the area default. This keeps repo-agnostic commands and `check-dossier` working from any folder, and still never pairs a dossier value with another repo's.
- The call's own value always wins. When the call names one per-repo input itself (`--repo x`), the call has chosen its target, so the dossier's other per-repo inputs that match nothing fall through as before: pairing them is the caller's call, and the parity suite's bitbucket examples (`--repo` only, with a per-repo `project` in the fixture dossier) rely on it. A call that names none of them is refused.
- `dossierConnection` (the dossier commands' connection check) treats such an input as unset, since it asks with no repo by design.
- Toil UI resolves with no repo folder, so a per-repo dossier now gets this error from its dashboard until it passes owner and repo itself (#542). Not changed here. #542 passes each area's context inputs explicitly per repo (GitHub, Bitbucket, Azure DevOps, Jira), so it must merge before this one.
- Only a folder that matches none of the dossier's repos is stranded; a matched repo the per-repo map leaves out (a map filled one repo at a time) keeps the old fall-through. Only the area's own context inputs count as the caller choosing a target, so a flag like `--fields` doesn't. `check-dossier` gets no `DOSSIER_REPO_UNMATCHED` warning, since it reads every per-repo value by design.
- The maintainer ruled this not a declared breaking change (2026-11-02, no CI users yet), so it ships as `fix:` with no contract version bump. `docs/command-contract.md`'s bump rule (commands, flags, data fields, envelope keys, error codes) wouldn't have bumped it anyway.
