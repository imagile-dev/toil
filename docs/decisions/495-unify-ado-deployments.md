# One CLI and MCP surface per product: Azure DevOps Server and Services (#495, slice 4)

The maintainer's decisions on #495 (2026-10-27) and slice 1's defaults (`495-unify-jira-deployments.md`) apply unchanged: one area per product with a `deployment` on the connection, config version 3, the old names removed with no deprecation period, the union surface with a clear refusal, variant-native `data`, a retired env var ignored when empty unless `TOIL_STRICT_ENV=true`, one section per product in a dossier, every save writing version 3, and a stale `TOIL_<AREA>_*` on a Services default refused unless `TOIL_ADO_DEPLOYMENT` is set. These are the defaults this slice chose within them.

- **Names.** `deployment` is `server` or `cloud`, defaulting to `server`, as for Jira (so `RENAMED_AREAS` says `ado-cloud` is `ado` with `deployment: cloud`, and every old form is refused by the machinery slice 1 built). The labels the refusals and help use are `Server` and `Services`, the vendor's own words for Azure DevOps Server and Azure DevOps Services. The file layout is Jira's: `area.ts`, `overrides.ts`, `server/`, `cloud/`.
- **`--collection` and `--organization` are Server's; Services has no collection.** Services' organization is the base URL (`https://dev.azure.com/<org>`), checked by the request hook before anything is sent, and a connection is one organization. Both stay group context inputs of the area, so Server's resolution (flag, dossier, git remote, connection) is untouched, and both declare `deployments: ['server']` (`ContextInput.deployments`, the mechanism the Bitbucket slice landed in core): a Services connection refuses them with `UNSUPPORTED` before any request, as it does `--parent`, and no per-route wrapper is needed. An input outside its `deployments` never takes a value from the connection's settings, `defaults.ado` or the git remote on the other deployment, only from the call or the dossier. A `collection` in `defaults.ado` is simply not used by a Services connection; it is not an error, because `defaults.ado` reaches both deployments by design.
- **A missing project or repo on Services is refused with its own words, by core, before the write gate.** Services' project and repo are `required` context on its commands, Server checks its own in `where()` (the contract's order and wording), and core now checks `required` per deployment, from the route the connection's deployment takes (`resolveCall`). `project` and `repo` carry `missing` wording (`No Azure DevOps project given. Pass --project <name>, or set project on the connection.`), and the fix is core's, naming the flag, the setting and its env var, as it always did. The earlier version of this slice moved that check into `run` (a per-route wrapper, `cloud/wrap.ts`, now deleted), so a Services write with both problems reported `WRITE_DISABLED` first; that cost is gone, the missing-project error comes before the write gate again, and the unadopted-dossier guard is unchanged.
- **The git remote: Server reads it, Services still doesn't.** Server's project, repo and collection come from a remote on the connection's host, by core's Azure DevOps remote parser. Services never read the remote (a Services remote is `dev.azure.com/<org>/<project>/_git/<repo>`, which the same parser would read correctly, but adding that is a feature, not a fold). The area's `git` reader returns nothing for a `cloud` connection, and the `project` and `repo` help says the remote is read on Server connections only. A dossier's `host` and a remote both select a connection by its host, so a Server host can't pick a Services connection or the reverse; the deployment of the connection that is picked decides the reader.
- **`--creator` and `--reviewer` are `<id>` on both.** Server's recorded spelling was `<alias>`, but its code has always sent the value as `searchCriteria.creatorId` and `reviewerId`, the identity id filter, and says so in its own help and tool description; nothing resolves an alias. So the idea is the same on both deployments and the flag is one: `--creator <id>`, `--reviewer <id>`. That is a spelling the contract recorded, so it is a divergence under principle 10 (`docs/divergences/ado.json`), as `--assignee <user>` was for Jira. The brief expected the help to say alias on Server; it would have said something the command doesn't do.
- **Two Server schemas were widened so one union serves both.** The union takes the first deployment's schema where the two differ. Server's `work-item create --priority` was text and Services' a whole number; Server's `pr update --draft` was text (`true`, anything else false) and Services' a boolean. Server's schemas now also accept a number and a boolean, which Server sends as it always sent them (the number as text, the boolean as `true`/`false`), and the CLI is unchanged because argv is text. Without it an MCP caller's `priority: 2` or `draft: false` was refused for Services. Services still validates its own call against its own schema.
- **Words that differ are reconciled in `overrides.ts`, keeping Server's where both mean the same.** The registry refuses to build until every shared command's descriptions, field texts and flags agree, so each pair is written once, with the deployment named where it matters. Two changes of meaning: `--reviewers` on `pr create` no longer says Server takes "display names", because the code sends the value as an id and always did; and `pr unapprove` says "Remove your vote", which is what both deployments do. `work-item comments` keeps both behaviours (Server reads the first page, Services every page with `--limit` and `--cursor`), each flag refused on the other.
- **Warning codes lose `CLOUD`.** `ADO_CLOUD_WORK_ITEMS_MISSING` is `ADO_WORK_ITEMS_MISSING`, the code Server already used for the same thing, and the two Services-only ones are `ADO_TYPE_UNKNOWN` and `ADO_DEFAULT_TEAM`. A prefix naming an area that no longer exists would be wrong in the unified one, and these are part of the declared breaking change. Nothing in Toil UI read them.
- **`SYSTEM_ACCESSTOKEN` is Server's; a Services default never takes it.** Azure Pipelines' job token is a CI fallback of `pat`, and applied to the area's default connection it would overwrite an organization-scoped token set in the file with a token that isn't one. The old `ado-cloud` never read it (its decision #222 says why), and the old `ado` did. The area uses core's `defineArea({ fallbackWhen })` (landed by the Bitbucket slice, applied in `applyAreaEnv`): a function of the default connection's effective settings (its own keys over `defaults.<area>`, the area's `TOIL_<AREA>_*` variables and the connection's `TOIL_CONN_` ones). For `ado` it is `effective.deployment !== 'cloud'`. The brief says to refuse an ambiguous fallback; this is not ambiguous (the connection's deployment is known) and refusing would fail every Azure Pipelines job that has a Services default, so the variable is skipped silently, which is exactly what `ado-cloud` did. `TOIL_ADO_*` aimed at a Services default is refused by slice 1's rule, unchanged. In a pipeline that maps the job token for Services, set `TOIL_ADO_DEPLOYMENT: cloud` beside `TOIL_ADO_PAT` and `TOIL_ADO_BASE_URL`. The Services variant declares `uses: ['team']`, so a connection that holds `team` without `deployment` is told to set `deployment` to `cloud`. Both deployments send the token as Basic with an empty user name, as before, and nothing else about authentication changed.
- **`work-item transition --to` was on both**, so there is nothing to union. The dossier pin key is `ado.transitions` for both; an `ado-cloud.transitions` pin in an old dossier is read as `ado.transitions` by the section fold, with its warning.
- **`work-item schema` is hand-registered, not folded.** It needs no connection, so there is no deployment to route it by. Services has no `--input-file`, so it prints Server's shape, the only one there is, and the skill says so. Unlike `jira issue schema` it takes no `--deployment`.
- **`ado api` is Services only**, as Server has no passthrough; on a Server connection it is `UNSUPPORTED`. Server-only commands (`pipeline`, `run`, `commit status`, `work-item assign|link|tag|…`, `check-dossier`, …) and Services-only ones (`sprint`, `backlog`, `board`, `pr threads`) are refused the same way on the other deployment.
- **Contract version stays 2.** No toil release contains #499 yet (the newest tag is `v0.1.0-beta.2`, cut before it), so one release carries all the slices; the history row for version 2 now names `ado-cloud` too.
- **Fixtures.** `AreaFixture.deployments` names `ado` and `ado-cloud` (connection names). Services' canned responses moved to `test/fixtures/ado-cloud-data.ts`, and every route of both is pinned to its own origin, because a Server route is a bare path pattern and a Services path starts at the organization. A `deployments` bite check (every `ado` example forced onto the Server connection) failed 153 of 840 `ado` parity tests, then passed again once restored.
- **OWI.** `ado-cloud` leaves `OWI_SOURCES`; `source.deployment` (slice 1) already carries it, and the Open Work Item docs say `jira` and `ado` have one.
- **Toil UI.** `ADO_AREAS` is `['ado']`; the command lists, `PR_HOSTS` (the Services entry goes and GitHub's index follows) and the sync tables (`SEARCHES`, `PR_GETS`, each keeping #503's `reconcile` flag) lose the `ado-cloud` names. The loader used to skip pipelines for Services because it had no pipeline commands and read its pull requests only when the dossier named a repository; it reads the same from the dossier's connection (`dossiers show`'s `connection.deployment`, in `ui/src/load.ts`), not from the items it loaded, so a Services dossier behaves as before even with no items yet, makes no pull request or pipeline calls it can't answer, and a Server one is untouched. The sub-task proposal says `ado work-item create` takes no parent on a Services connection, from `source.deployment`. `ui/scripts/ado-seed/` reads `TOIL_ADO_BASE_URL`, `TOIL_ADO_PAT` and `TOIL_ADO_PROJECT` (it was the `TOIL_ADO_CLOUD_*` set), `real-home.mjs` sets `TOIL_ADO_DEPLOYMENT=cloud` for the connection it makes, and `items.owi.json` is regenerated (`area: ado`, `deployment: cloud`). As the last fold, the stale `ado-cloud` comments in `format.ts`, `delivery.ts` and `people.ts` are cleaned, `people.ts` drops its `-cloud` family stripping (a person's `ado` identity is the one for the `ado` area), and the menu's Briefing (`src/welcome/views/briefing.ts`) and `load-window.test.ts` stop naming the retired area and its folder.
- **Site and skill.** One `ado` skill page and one integration entry (`Azure DevOps`, level `unit` for both), with the retired `ado-cloud` page, data and command files gone, and a redirect from `/connect/ado-cloud/`. `skills/toil/ado.md` has a "Server and Services" table and a "Moving from `ado-cloud`" section.
- **The maintainer's own shell.** `TOIL_ADO_CLOUD_BASE_URL` and `TOIL_ADO_CLOUD_PAT` are exported there, and every toil command now fails with `CONFIG_INVALID` until they are renamed (`TOIL_ADO_BASE_URL`, `TOIL_ADO_PAT`, `TOIL_ADO_DEPLOYMENT=cloud`). The tests were run with them unset.
- **Not verified.** No Windows, macOS or Node 26 run (CI's platform workflow covers them), and no live Azure DevOps Server or Services; the unit level is unchanged for both.
