# Toil UI's briefing, its drawer, and how Analyze briefs a dossier (#494)

- The Overview's address and export stay, and its body becomes the briefing, so every link, palette entry and test that opened a dossier's home still does. The old code recommendation (`ui/src/model/recommend.ts`) is removed: toil's briefing by code (`src/core/brief/`) replaces it, and Toil UI calls the pure function directly, as it already does for `util owi similar`'s scorer, rather than through `execute()` with the records serialized. Readiness and builds, which the old recommendation weighed, aren't OWI yet; they stay on the Board, the Command Center and the item page.
- The compact critical-chain chart left the home page with the key-issue cards; the Dependencies tab already draws the whole blocker timeline, one link away, so the compact chart was removed rather than kept unused.
- The home page shows Analyze's briefing only when the latest Analyze is current (made since the data was read, or the same UTC day) and answered with a briefing block; otherwise the code's, saying why. The same rule the Overview used for its recommendation (#395).
- Two checks keep an agent's briefing honest on the page: an id it names that isn't the dossier's is shown in red as unverified, and every item the code flagged that it put under no reason and didn't leave out is listed one step in, "Flagged by code, not in the briefing". With "Left out by the dossier's focus", this is how the maintainer's decision on #494 (show what "leave out" hid) reaches the screen. The server's citation check also covers the ids inside the briefing block.
- A focus from a dossier the reader hasn't adopted shows its file on the briefing's top line. The dossier's file and whether it's adopted come from `dossiers show`, which the loader already calls (`DossierData.origin`).
- The drawer has an address: the page's own path plus `?item=<owi id>` (`Route.peek`), so a peek can be shared, Back closes it, and the view behind it stays put. At 1200px and wider it takes the Agents sidebar's column; below that it covers the view from the right. Escape closes it, registered in the shortcut table as `drawerClose`.
- Item links on the briefing open the drawer through a context (`ItemHrefContext`), so `Cited` and `ItemLink` needn't change their callers; a Board card's key and Pull requests' item links do the same. The card menu's Open, the drawer's Open, and every other view still go to the item's page.
- The server lifts the briefing block out of Analyze's answer into `answer.briefing`, so the chat and the analysis page lay it out instead of showing JSON; the analysis record keeps it, and its recommendation and first three reasons fill the history's existing `recommendation` and `issues`, so the Analyses list and "what changed" keep working. Older analyses, and the sample's earlier one, still read with `structureOf`.
- Analyze's question comes from toil (`dossiers analyze prompt --host toil-ui`). With a toil that lacks the command (Toil UI ahead of its release), the server falls back to the question it kept before and adds a warning to the answer saying so.
- The sample's scripted Analyze answers with a briefing block, holding only facts the scripted evidence already states; its on-track counts and "changed" lines are left out, so the page shows the code's count rather than an invented one.
- How Analyze briefs a dossier is a form in Settings → Dossiers, with its own address (`#/settings/dossiers/<name>/analyze`), reached also from Customize and the command palette. It shows the prompt as it will be sent, composed by toil's own `analyzePrompt` from the form's draft before anything is saved, and saves with `dossiers analyze set`, added to `CONFIG_CHANGES`. Clearing a setting stays CLI only, as in toil.
- Customize is per person and per browser (`ui/src/briefing-prefs.ts`, `localStorage`, wrapped so blocked storage leaves the defaults): open the first reason, numbers open, reasons hidden (counted on the On track line), item opens in the drawer or on its page, and Analyze after each sync. They're conveniences for the person at the screen, never what Analyze looks for.
- "Run Analyze after each sync" is off by default (the maintainer's call on #494) and runs in the page, not the server: when a finished sync's `news` id changes and the chat isn't busy. It never runs for the sync already there when the page opened, and never on a timer. Keeping it out of `ui/server/sync.ts` also keeps it clear of #493's sync rework.
- The welcome menu's Briefing composes the reads itself, as Toil UI's loader does, rather than through a new toil command that gathers a dossier's work, which principle 3 rules out: each tracker's issues and each code host's open pull requests, then each open pull request with `pr get --include reviews,checks` (at most 20), then `util owi map` with key patterns taken from the Jira issues it read, then `dossiers brief`. Each is a step on a result screen showing the line it ran; a `--text` carrying the steps' output is named on screen ("<N results from the steps above>") rather than printed. Azure DevOps work items, which take a query and a read each, are left to Toil UI, and the first run's title says so. Jira is matched by area family (`jira`, `jira-*`), so the reads hold when #495 folds `jira-cloud` into `jira`.
- Keys on the menu's briefing are OSC 8 hyperlinks only in terminals known to draw them (Windows Terminal, VS Code, iTerm2, WezTerm, Ghostty, VTE 0.50 and later); every other terminal gets the URL printed under each item, since an unknown one may print the escape as text. `Brief this dossier` is the dossier screen's last row, so the rows a hand already knows keep their places.
