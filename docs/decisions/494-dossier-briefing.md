# The dossier briefing and its Analyze settings (#494)

- Slices 1 and 2 of #494 (the briefing by code; the dossier's Analyze settings and the prompt) ship as one PR. Both are toil-side, slice 2's settings already decide what `dossiers brief` applies, and the maintainer prefers larger vertical PRs.
- `toil dossiers brief` takes Open Work Item records from stdin, `--file` or `--text`, and contacts no service. Gathering the dossier's items and pull requests is left to the caller (`<tracker> … | util owi map`), so one command doesn't decide which services to ask (principle 3). It reads the dossier for its settings: `wipLimit` and the `analyze` key.
- The file flag is `--file` (field `file`), one name on both front doors, rather than `--input-file`, which the jira and ado areas use for a request body (principle review).
- The lenses are computed from OWI fields alone: failing checks and review waits from a pull request's `checks`, `checksAt`, `created` and `firstReviewAt`; blocked from `blocks` links; stale from `updated`; load from `assignee` and `wipLimit`; drift from a pull request's state against its item's. Builds and deployments, which Toil UI reads from Jenkins, Azure Pipelines and OpenShift, aren't OWI yet, so "failing" here means a pull request's checks, not a pipeline run. Toil UI's per-card insights keep using its builds and deployments.
- A lens that can't test an item for a missing field (no `updated`, no assignee, a pull request read by `pr list`, whose checks and reviews are unmapped) doesn't count it as on track for that lens: `lenses[].untested` counts such items and `note` says which field and how to read it (principle review, principle 4). A failing pull request with no `checksAt` is untested, not flagged.
- Each finding keeps its record's `source` (area, connection, command), and each pull request its `repo` (principle review, principle 4).
- Readiness stays off in the standard lenses and isn't computed by toil: the readiness checks live in Toil UI. `lenses` lists it as off.
- An item goes under the first lens in the dossier's order that flags it, so it appears once. Done items are counted as on track, except under drift, where "done while its pull request is open" is the point.
- Within a reason, items holding up the most open work come first (`holds`, counted down `blocks` chains, safe on a cycle), and the first reason's first item becomes the recommendation. A plain template per lens writes the recommendation; Analyze writes a better one.
- The sprint is the iteration most open items are in, by its dates or the tracker's `current`; items join it only with the same name, start and end, since two trackers may each have a "Sprint 42". An end at exactly midnight UTC (Azure DevOps' `finishDate`) is read as the end of that day. Its pace isn't judged until a quarter of it, and at least a working day, has gone, because stories finish late in a sprint: the sandbox's Sprint 43, one day in with nothing done, read as "none land at this pace" before this rule. A sprint with no estimated points says so in its lens's note.
- Default thresholds: failing checks after 24 hours, a first review after 2 working days, stale after 5 days, drift after a merge more than a working day old. Toil UI's `FAILING_HOURS`, `PICKUP_DAYS` and `STALE_DAYS` now read these from toil's lens definitions, and its `workingDays` is toil's (`src/core/brief/time.ts`), so the CLI and Toil UI agree. The first draft said 4 hours for failing checks; 24 is what Toil UI already showed ("over a day"), so nothing on screen changes.
- The reader accepts several JSON documents run together, pretty-printed or not, so `cat items.owi.json prs.owi.json` works with `--pretty` output; it drops a malformed link and an estimate whose value isn't a number rather than letting either skew a total (code review).
- `BRIEF_UNLINKED_CHANGES` warns when pull requests name no work item in the input, which is what a wrong `--key-pattern` looks like (code review).
- The dossier's `analyze` key: `goal`, `audience` (`lead`, `engineer`, `stakeholder`; `lead` by default), `lenses` (`{ id, on, threshold }` in order; unlisted lenses follow in the standard order), `watchFor` and `leaveOut`. Texts are at most 1000 characters and refused when shaped like a credential, as every dossier value is. `leaveOut` stays words for the agent, not a filter in code; the prompt makes the agent list what it left out (the maintainer's decision on #494), and slice 3 will show Toil UI's reader what the code flagged that Analyze didn't mention.
- `toil dossiers analyze set` lives with the other dossier writers (`build.ts`): a value already set needs `--replace`, and `--clear` / `--reset` are deletes, CLI only, the way `wip-limit --clear` is. It's a local write with no `--allow-write`, so an agent may tune a dossier over MCP; that can change what Analyze is told, never what it may do (its tools stay read-only, and proposals still need a person).
- A focus from a dossier the reader hasn't adopted is used, and the prompt names where it came from: the dossier, the repository folder it's checked into (from its path, so no git is needed), and that the reader hasn't adopted it (the maintainer's decision on #494).
- The Analyze prompt has two hosts: `toil-mcp` (any agent with toil's tools; it gets the steps to read and brief the dossier, and answers in Markdown with every item linked to its url) and `toil-ui` (Toil UI's agent, which answers with a ```briefing JSON block that `src/core/brief/answer.ts` reads back and checks). `toil mcp` serves the first as the prompt `analyze`, built by the `dossiers_analyze_prompt` tool and served exactly when that tool is.
- The parity suite's fixture for commands outside an area now holds one workspace file, `owi/brief.owi.json`, so an example covers `--file`.
- The welcome menu's Briefing view isn't in this PR. It needs a dossier's items gathered in the terminal, and the reads Toil UI makes for that are in `ui/src/load.ts`, which toil can't import; it's done as its own slice once #495 settles the Jira reads (raised on the session, 2026-10-27).
- The output of `dossiers brief` and `dossiers analyze` becomes a contract at the next release (principle 7). It's additive now; Toil UI and agents can build on it before slices 3 and 4, and any reshape after release is a declared change.
