# Jira Cloud sprint commands (#561)

- **`jira sprint get | create | update | start | complete` are Cloud only.** Data Center's Agile API has the same endpoints, but nothing here was run against one, so a Data Center connection gets `UNSUPPORTED` before any request, as `project list` does. They are additive: the contract records none of them, so no divergence entry.
- **All four changes are writes and none is a DELETE,** so they are `writes: true`, take `--allow-write`, and are served over MCP. `complete` closes a sprint, which Jira does not undo, but it deletes nothing.
- **`update` uses the partial-update `POST /sprint/{id}`, not `PUT`,** so a field you leave out is left alone. `PUT` blanks what it isn't sent.
- **`start` refuses a sprint that is not `future`, and one with no end date,** before anything changes. Jira needs both dates to start, and a silent default length would be a guess about a team's cadence. Start defaults to now; end to the sprint's planned end.
- **`complete --move-open-to <sprint|backlog>` moves the issues whose status category is not Done first, then closes the sprint.** The order matters: a target sprint must still be open, and a failed close leaves the issues in a sprint they were headed out of, which is recoverable, where the reverse is not. Without the flag nothing moves: checked live, an open issue stays on the sprint after it closes (it then matches `sprint in closedSprints()`), so moving them is opt-in and says what it did in `moved`. `--move-open-to` takes a sprint id or `backlog`, since one flag with two shapes was simpler than two flags.
- **Batches of 50** for moves, the most Jira's sprint and backlog endpoints take.
- **Verified live on a Jira Cloud sandbox** (create, start, complete to another sprint and to the backlog, on a throwaway sprint each; a second sprint starting while another was active was allowed, which depends on the site's parallel-sprints setting and is passed through when it is not).
- **Found, not fixed: Toil UI's Jira cards show no sprint or points until the connection registers `customFields`.** `jira issue search` returns only its standard fields plus registered custom fields, so `util owi map` cannot find "Sprint" or "Story point estimate" and says so in `unmapped`. Registering `{ "id": "customfield_10016", "name": "Story point estimate", "type": "number" }` and the Sprint field (ids from `jira issue fields --discover --custom-only`) makes the sprint line and the points appear. The same standard-fields list leaves out `issuelinks`, so "blocked" reads 0 for Jira even where `Blocks` links exist. Both are for a follow-up, since changing a search's default fields changes what every caller receives.
- **Found, not fixed: `--field customfield_10016=2` sends the number as the string `"2"` and Jira Cloud refuses it,** because an unregistered field has no type to read. A numeric value through `--input-file` works, as does registering the field as `number`.
