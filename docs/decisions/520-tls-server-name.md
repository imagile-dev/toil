# A TLS server name and a CA file for database connections (#520)

- Two new optional `db` connection keys, `tlsServerName` and `tlsCaFile`, both needing `"ssl": true`. Neither can weaken verification: `tlsServerName` changes which name the certificate is checked against (chain and name, `rejectUnauthorized` on), and `tlsCaFile` only adds trust anchors. There is no key that skips the name check or the chain, and none was added.
- One place validates both (`src/core/db/tls.ts`, called from the area schema's `superRefine`), not each engine: they need `ssl`, an engine that can honour them says so with `DbProvider.tlsSettings`, and an engine that can't is refused with the supporting engines named. The name must be a bare DNS host name (no IP, wildcard, scheme, port, path, user or space); the file path must be absolute, with no `~` expansion.
- Supporting engines: PostgreSQL, MySQL and MariaDB, SQL Server, Hive and Impala. Oracle, Teradata and SQLite refuse both. Oracle's Thin mode takes its CAs from Node's process-wide defaults (`trustOsStoreByDefault` sets them), so adding a file's certificates there would trust them for every connection in a long-lived `toil mcp`, breaking "for that connection only"; and Thin mode offers no clean per-connection servername, only `SSL_SERVER_DN_MATCH` on the listener's own certificate. Teradata goes through core's `fetch` (the OS store and proxy) and SQLite has no network.
- How each driver is made to verify against the name, read from the drivers' code:
  - `pg` sets `servername` itself after merging the `ssl` object, so `ssl.servername` is overwritten for a DNS host. Passing `host: <tlsServerName>` makes pg send it as SNI and verify against it with Node's own default check, and pg's `stream` option hands it a socket whose `connect(port, name)` is redirected to the real host (`socketToOnConnect`). No `checkServerIdentity` override was needed, so none was written.
  - `mysql2` derives SNI and the identity check from `config.host`, with no override. Same route: `host: <tlsServerName>` plus a `stream` function returning a socket to the real host and port (`socketTo`), with `rejectUnauthorized` and `verifyIdentity` untouched.
  - `tedious` has `options.serverName`, used for both SNI and the identity check in its classic `encrypt: true` path (`message-io.js` `startTls`: `host` and `servername` are both the name). It is passed as it is.
  - Hive and Impala (toil's own client): `tls.connect` gets `servername` and an explicit `checkServerIdentity` against the name, with the socket still going to `host`.
- Error messages and debug lines name the real host. The debug line says `TLS, verifying <name>` when the name is set, and `TLS, trusting N certificate(s) from <path>` when a file is. Neither prints a file's contents.
- `tlsCaFile` is read with `node:fs` when a call connects, not when config loads, so a missing file never stops `connections list` or `remove`. Who may set it is the maintainer's call (2026-10-29): it is an ordinary non-secret setting, so an agent may propose it through `connections add --set` on the person's yes, like `host` and `tlsServerName`; the approval is the gate, as for every other setting. It is a new documented exception to the file workspace bound, `db.tls-ca-file` in `docs/bounds.md` and `src/core/bounds.ts`: it is named by the connection's settings, never by a command's input; at most 1 MB, enforced while reading through the descriptor and only for a regular file; network, device, `~/.toil`, `--config`, `/proc` and `/sys` paths are refused with the same helpers `files.ts` uses (`remotePathKind`, `nodeFiles` with `protect`), and a Windows path needs a drive letter; only `-----BEGIN CERTIFICATE-----` blocks are used, each parsed by `crypto.X509Certificate`; a file with none (a config, a key) is refused without quoting a byte. The certificates are trust anchors for that one connection's socket and go nowhere else.
- `src/core/db/tls.ts` is added to the triage safety layer's list (`scripts/triage/changes.mjs`), since the bounds docs name it and a test holds the two together.
- mysql2 reported a failed certificate check as a generic `DATABASE` error with the wrong fix. It is now `NETWORK`, matched on mysql2's `HANDSHAKE_SSL_ERROR` code (set for every TLS handshake failure), with its own words kept in the message and the TLS fix; the TLS fixes for the four engines also name `tlsCaFile` and `tlsServerName`.
- The skill's cloud CA section gives `tlsCaFile` (one connection), `NODE_EXTRA_CA_CERTS` (every Node program, with the steps for Windows, macOS and Linux and the note that Node reads it only at startup) and the OS store (machine-wide) as three equal routes. The existing `NODE_EXTRA_CA_CERTS` text in the settings tables and `core.md` is kept.
- Azure SQL: tedious follows a Redirect to a worker node and verifies it against `serverName`, so it fails closed there; the docs say to use the Proxy connection policy with `tlsServerName`.
- `Context.ownFiles` (toil's config folder and `--config` file) is new, handed to db providers as `DbCall.protect`, so `tlsCaFile` can refuse them without a provider reading config.
- `test/db/tls-handshake.test.ts` runs a real handshake on loopback through pg's client config, with a throwaway CA, key and certificate in `test/fixtures/tls/` (valid 100 years, labelled test only). mysql2 has no equivalent loopback test: its handshake needs a server that speaks MySQL's, so MySQL rests on the Docker run.
- Not run: SQL Server, Hive and Impala against a real server with a throwaway certificate (PostgreSQL and MySQL were). Their drivers are held by unit tests on the options they receive, and tedious and Node's code were read for the verification they do with them.
