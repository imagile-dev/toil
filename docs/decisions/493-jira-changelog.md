# Jira changelog inline in `issue search`, and Toil UI's sync using it (#493, step 3 Jira)

Defaults this slice chose; the maintainer's decisions on #493 are not repeated.

- **The flag is `--changelog` (`changelog: boolean`), on `jira issue search` for both deployments.** It names what comes back (the changelog, Jira's own word and the key it appears under in the issue), not how it is asked for (`--expand changelog`, which would invite `--expand names`, `--expand schema` and the rest of Jira's grab bag through a door nobody asked to open). Off by default, so without it the request and the output are exactly what they were. Additive, so `docs/command-contract.json` and `docs/divergences/jira.json` gain nothing (`--updated-since` was added the same way); `test/contract.test.ts` passes untouched.
- **Data Center sends `"expand": ["changelog"]` in the POST body of `/rest/api/2/search`; Cloud sends `"expand": "changelog"` in the POST body of `/rest/api/3/search/jql`.** Data Center's search request takes `expand` as a list of strings, the enhanced search takes a comma-separated string. Both are in the body because both searches are already `queryByPost`. Each issue keeps Jira's own `changelog` object (`startAt`, `maxResults`, `total`, `histories`) unchanged, so the data stays variant-native; custom-field translation and `--fields` touch `fields` only and are unaffected.
- **Caps: toil returns what Jira sent and warns once that some issues may be cut short.** Atlassian documents Cloud's `changelog.total` in the search as "the number of results on the page" and RFC-61 caps it at 20 entries per issue, so `total > histories.length` never fires there and a history cut at 20 looks whole. An issue therefore counts as possibly cut short when `total > histories.length`, or `histories.length >= maxResults` (the page is full), or `total` or `maxResults` is missing. One `meta.warnings` entry (`JIRA_CHANGELOG_TRUNCATED`, `JIRA_CLOUD_CHANGELOG_TRUNCATED` on Cloud) says how many issues may be cut short and that `jira issue history <key>` reads the whole history. The wording is "may" because a full page can also be an exactly-full history. toil does not top the history up itself: one command, one source (principle 3), and the caller knows whether it wants the extra calls.
- **Unverified, to check against a live instance (recorded as suspected items on the Jira suspected-bug issues, not guessed):** (1) the cap on Cloud is 20 per RFC-61 (documented); Data Center's cap and order of an inline changelog are undocumented; (2) whether Cloud's search returns `changelog.total` at all, and as the page count the spec says: absent means the issue is treated as possibly cut short, so it costs a call, never a short history; (3) resolved: Cloud's inline `histories` run newest first (the spec), against `/changelog`, oldest first, and Toil UI's adapter turns a newest-first list round; (4) whether a Cloud search request that asks for `changelog` lowers the page size Jira will accept for `maxResults`.
- **Toil UI asks for `changelog: true` on its one Jira search and keeps a per-issue fallback.** An inline changelog counts as whole only when `total` is a number equal to the entries sent and `maxResults` is a number the entries stay below. Anything else (a cut `total`, a full page, a missing `total` or `maxResults`) is read with `jira issue history <key>` through the existing pool, so a truncated history is never mapped as if it were whole; the worst case is the old one call per issue. An older toil that does not know `changelog` refuses it as an unknown field and the search fails; it does not degrade silently. The fallback uses the sync's existing machinery unchanged: `HISTORIES` still skips an unchanged issue's cached history.
- **The adapter is `splitChangelogs` (`ui/src/jira-changelog.ts`), and it gives `mapOwi` the input it always had.** `mapOwi` puts the issue itself under `native` and a history under `native` too, so handing it issues with `changelog` still on them would change every item. The adapter returns the search with `changelog` taken off each issue, and for each whole changelog a `{ key, history }` wrapper whose envelope is the search's own with `meta.command` set to `jira issue history`, `data` set to the histories, and `meta.page` and `meta.warnings` dropped. It reads the history entries oldest first, the order `issue history` lists them, and turns a list that runs newest first round (compared on its first and last `created`), because Cloud's inline order is newest first and Data Center's is undocumented. `ui/test/jira-changelog.test.ts` holds `mapOwi`'s items and warnings to be equal both ways on the sprint fixture, and equal again from a reversed list.
- **The sync keeps its shape.** The search is still in `SEARCHES`; the delta search carries `changelog: true` with `updatedSince`, so changed issues arrive with fresh histories and unchanged ones keep theirs from the merged answer. The daily reconcile's ids-only listing (`idsOnly`) now drops `changelog` as well as asking for `fields: key`, since a listing to reconcile with reads no histories. The cache key for the search changes with the input, so the first sync after an upgrade lists the window whole once.
- **The cached search response is larger, and is rewritten whole when any issue in it changes.** It now carries every issue's changelog, which used to live in one row per issue, so a sync that changes one issue rewrites the whole search row. At fixture sizes, 2000 issues of 20 entries each is about 16 MB per rewrite (the scale sim measures about 390 KB per rewrite for 200 issues of short histories, and reports response bytes written). Restructuring storage so the histories are not part of the search row is left for if it hurts in practice. First sync: 200 live issues wrote 655 rows instead of 855.
- **Fixtures.** The sample's `jira issue search` is canned with `changelog: true` only (the old, input-without-it entry went, since `registry.test.ts` requires every canned call to be asked for); its inline changelogs are the fixture's histories, and PAY-106 is cut short on purpose (first entry sent, `total` 2) so `--sample` still exercises the fallback and the one `jira issue history` entry that stays canned is asked for. The sample renders the same items and transitions as before. The Toil UI stub answers the ids-only listing from that one canned search.
- **Pinning: no change.** Toil UI pins `@imagile-dev/toil` exactly and never releases ahead of the toil it needs (CLAUDE.md, Delivery). `ui/` on `main` may use commands the pinned toil lacks, and `npm run verify:ui` and the sync tests run Toil UI on toil built from the checkout. A `toil-ui-v…` release that includes this change goes out with or after the toil release that has `--changelog`, and bumps the pin in that release PR. The pinned toil (0.1.0-beta.2) rejects `changelog` as an unknown field, so Toil UI built from this commit must not be run against it.
- **The scale sim models Cloud's cap** (`ui/test/scale-sim.ts`, `ui/test/sync-scale.test.ts`): `maxResults: 20`, at most 20 entries newest first, `total` the page count, and one issue in ten with a 30-entry history. A first sync of 200 live issues makes 37 calls (2 searches and 20 `issue history`), against 17 when every history was short; the 20 extra are exactly the issues whose history the search cut, which the earlier `total > histories.length` rule would have mapped short without a word. The same sim reports response bytes written per sync.
