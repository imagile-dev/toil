# Jira changelog inline in `issue search`, and Toil UI's sync using it (#493, step 3 Jira)

Defaults this slice chose; the maintainer's decisions on #493 are not repeated.

- **The flag is `--changelog` (`changelog: boolean`), on `jira issue search` for both deployments.** It names what comes back (the changelog, Jira's own word and the key it appears under in the issue), not how it is asked for (`--expand changelog`, which would invite `--expand names`, `--expand schema` and the rest of Jira's grab bag through a door nobody asked to open). Off by default, so without it the request and the output are exactly what they were. Additive, so `docs/command-contract.json` and `docs/divergences/jira.json` gain nothing (`--updated-since` was added the same way); `test/contract.test.ts` passes untouched.
- **Data Center sends `"expand": ["changelog"]` in the POST body of `/rest/api/2/search`; Cloud sends `"expand": "changelog"` in the POST body of `/rest/api/3/search/jql`.** Data Center's search request takes `expand` as a list of strings, the enhanced search takes a comma-separated string. Both are in the body because both searches are already `queryByPost`. Each issue keeps Jira's own `changelog` object (`startAt`, `maxResults`, `total`, `histories`) unchanged, so the data stays variant-native; custom-field translation and `--fields` touch `fields` only and are unaffected.
- **Caps: toil returns what Jira sent and warns once.** When any issue's `changelog.total` is more than the `histories` sent, one `meta.warnings` entry (`JIRA_CHANGELOG_TRUNCATED`, `JIRA_CLOUD_CHANGELOG_TRUNCATED` on Cloud) says how many of the issues came back short and that `jira issue history <key>` reads the whole history. toil does not top the history up itself: one command, one source (principle 3), and the caller knows whether it wants the extra calls. `total > histories.length` is the test; the page's own `maxResults` is not compared with `total`, because the first says what is missing and the second only says why.
- **Unverified, to check against a live instance (recorded as suspected items, not guessed):** (1) the size at which each API cuts an inline changelog (the `issue` GET answers with the whole history on Data Center; the search is believed to cap at 100 entries per issue, on both deployments); (2) whether the enhanced search on Cloud returns `changelog.total` at all, which this slice relies on to see a cut (if it is absent, an inline changelog is treated as whole, and Toil UI would map a short one as complete); (3) the order of `histories` in the search answer on Cloud (the `/changelog` endpoint is oldest first; the inline order is not documented where this was checked); (4) whether a Cloud search request that asks for `changelog` lowers the page size Jira will accept for `maxResults`.
- **Toil UI asks for `changelog: true` on its one Jira search and keeps a per-issue fallback.** An issue whose inline changelog is missing or shorter than its `total` is read with `jira issue history <key>` through the existing pool, so a truncated history is never mapped as if it were whole, and an older toil that sent no changelog degrades to the old behaviour rather than to short histories. The fallback uses the sync's existing machinery unchanged: `HISTORIES` still skips an unchanged issue's cached history.
- **The adapter is `splitChangelogs` (`ui/src/jira-changelog.ts`), and it gives `mapOwi` the input it always had.** `mapOwi` puts the issue itself under `native` and a history under `native` too, so handing it issues with `changelog` still on them would change every item. The adapter returns the search with `changelog` taken off each issue, and for each whole changelog a `{ key, history }` wrapper whose envelope is the search's own with `meta.command` set to `jira issue history`, `data` set to the histories, and `meta.page` and `meta.warnings` dropped. It reads the history entries oldest first, the order `issue history` lists them, and turns a list that runs newest first round (compared on its first and last `created`), because the inline order on Cloud is one of the unverified items. `ui/test/jira-changelog.test.ts` holds `mapOwi`'s items and warnings to be equal both ways on the sprint fixture, and equal again from a reversed list.
- **The sync keeps its shape.** The search is still in `SEARCHES`; the delta search carries `changelog: true` with `updatedSince`, so changed issues arrive with fresh histories and unchanged ones keep theirs from the merged answer. The daily reconcile's ids-only listing (`idsOnly`) now drops `changelog` as well as asking for `fields: key`, since a listing to reconcile with reads no histories. The cache key for the search changes with the input, so the first sync after an upgrade lists the window whole once.
- **The cached search response is larger** (it now holds the histories it used to hold as one response per issue). That is the same bytes in fewer rows: 200 live issues wrote 655 rows on a first sync instead of 855.
- **Fixtures.** The sample's `jira issue search` is canned with `changelog: true` only (the old, input-without-it entry went, since `registry.test.ts` requires every canned call to be asked for); its inline changelogs are the fixture's histories, and PAY-106 is cut short on purpose (first entry sent, `total` 2) so `--sample` still exercises the fallback and the one `jira issue history` entry that stays canned is asked for. The sample renders the same items and transitions as before. The Toil UI stub answers the ids-only listing from that one canned search.
- **Pinning: no change.** Toil UI pins `@imagile-dev/toil` exactly and never releases ahead of the toil it needs (CLAUDE.md, Delivery). `ui/` on `main` may use commands the pinned toil lacks, and `npm run verify:ui` and the sync tests run Toil UI on toil built from the checkout. A `toil-ui-v…` release that includes this change goes out with or after the toil release that has `--changelog`, and bumps the pin in that release PR. The pinned toil (0.1.0-beta.2) rejects `changelog` as an unknown field, so Toil UI built from this commit must not be run against it.
