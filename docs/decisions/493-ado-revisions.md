# Azure DevOps revision feed, and Toil UI's sync using it (#493, step 3 Azure DevOps)

Defaults this slice chose; the maintainer's decisions on #493 are not repeated.

## toil

- **The command is `ado work-item revisions`, on both deployments, with `--updated-since`, `--fields`, `--limit` and `--cursor`.** It is every revision of every work item in the project, so it sits under `work-item` beside `history` (one item's revisions). `--updated-since` is the flag the area already uses for "changed since" (`work-item search`, `pr list`), not a new `--since` (principle 10), with the same date forms, validated by the same `wiqlInstant`. `--fields` is `work-item get-many`'s. It needs a project (the feed is read per project, so a move between projects is not hidden in it). Additive: `docs/command-contract.json` and the divergences gain nothing, and `test/contract.test.ts` passes untouched.
- **Data is an array of `{ id, rev, fields }`, as the feed's `values`.** Paging is toil's own: `meta.page.nextCursor` is the feed's continuation token (core's cursor encoding), so `--limit` and `--cursor` behave as on `work-item comments`. Without `--limit` every batch is read to `isLastBatch`. The token is not followed once `isLastBatch` is true (the feed sends one then as a watermark to poll from; toil does not hand it out).
- **`startDateTime` goes on the first request only.** Microsoft: "Cannot be used in conjunction with 'watermark' parameter". Every request carries `api-version` and `fields`; the first also `startDateTime`; later ones `continuationToken`. A resumed cursor therefore sends no start date.
- **People are `Name <email>` text; toil does not send `includeIdentityRef`.** With it the feed's identity is `{ id, uniqueName }` and no `displayName` (the reference's own example), which `mapOwi` would read as a different person from `work-item history`'s. The text form maps to the same person (`ui/test/ado-revisions.test.ts`). Long text fields (the description) are not in the feed unless `$expand=fields`, which toil does not send; Toil UI does not need them.
- **Requests, per deployment** (both `GET`, both `api-version=7.1`, the version the area pins):
  - Services: `{org}/{project}/_apis/wit/reporting/workitemrevisions?api-version=7.1[&fields=…][&startDateTime=2026-09-01T00%3A00%3A00.000Z]`, then the same with `&continuationToken=…` and no start date.
  - Server: `{collection}/{project}/_apis/wit/reporting/workitemrevisions?` with the same query.
  - Server goes through its `raw` request (no 429 retry, as every Server list the contract records), Services through its hook with retry.
- **API facts relied on, from Microsoft's public reference** (https://learn.microsoft.com/en-us/rest/api/azure/devops/wit/reporting-work-item-revisions/read-reporting-revisions-get?view=azure-devops-rest-7.1): the URI above; `startDateTime`, `continuationToken`, `fields`, `includeIdentityRef`, `includeDeleted`, `includeLatestOnly`, `$expand`, `$maxPageSize`, `types`; the response `values`, `continuationToken`, `isLastBatch`, `nextLink`; the example revisions carry `System.Id`, `System.Rev`, `System.State`, `System.IterationPath`, `System.ChangedDate` and `System.ChangedBy` (text, `Jamal Hartnett <fabrikamfiber4@hotmail.com>`) for every revision; "Project-scoped requests will only return work item revisions from the specified project" (https://learn.microsoft.com/en-us/rest/api/azure/devops/wit/reporting-work-item-revisions?view=azure-devops-server-rest-5.0). Server versions: the operation is documented for Azure DevOps Server 2019 (REST 5.0), 2020 (6.0), 2022 (7.0) and 7.1 (pages for `azure-devops-server-rest-5.0`, `-6.0`, `-7.0`, `-7.1` exist for it), so it exists wherever `api-version=7.1` does; an older Server answers the area's "too old" error as for every command.
- **Unverified, to check against a live instance (appended to the Azure DevOps suspected-bug issue):** (1) that `rev` runs 1, 2, 3 … with no skipped number for one item (the completeness rule below survives a skip by reading the item with `work-item history`, so a skip costs a call, never a short history); (2) that `"System.ChangedBy"` text is always `Name <unique name>` and that this maps to the same person as the identity object on both deployments (Toil UI reads any other text through `work-item history`); (3) that `fields` omitted returns the iteration path and every field a dossier's `fields` map could name (Toil UI reads every item through `work-item history` when the dossier maps its own iteration field); (4) the default and cap of `$maxPageSize` (not sent; the scale numbers assume 200 revisions a batch); (5) whether a revision's `startDateTime` filter compares `System.ChangedDate` or `System.RevisedDate`, and whether it is strict; (6) that a feed read from a watermark returns every revision made after it, however late it was committed (Toil UI's SKEW margin and the completeness rule are the safety net); (7) that `types` and `includeDeleted` do nothing here (not sent); (8) that Server answers `isLastBatch` the same way; (9) that a revision already read is not changed by a later one except `System.RevisedDate` (Toil UI lays a delta over the cached feed by item and revision, and `mapOwi` does not read `System.RevisedDate`).
- **Tests:** the exact request per deployment, the paging with and without the start date, `--limit` stopping inside a batch and the cursor resuming, a zoneless date and a bare `--cursor` refused before any request, and a cancel between batches stopping with `CANCELLED` (`src/areas/ado/cloud/cloud.test.ts`, `src/areas/ado/server/paging.test.ts`). Parity: an example per shape and fixture routes on both deployments.

## Toil UI

- **The loader reads one feed after `get-many` and maps an item from it only when the feed holds the item's whole history** (`ui/src/ado-revisions.ts`). The rule: the item's revisions in the feed are exactly 1 to the item's own `rev` as `get-many` read it. That is stronger than "`System.CreatedDate` is at or after the feed's start": the date says the first revision should be there, the run says every one is, and it also catches a gap the watermark missed, a feed ahead of `get-many`, an item moved from another project (project-scoped feed) and an open item nobody touched since the window opened (no revisions at all). Any other item is read with `work-item history` through the existing pool. The feed starts a day before the window opens (`windowDays + 1`), to cover WIQL's `@Today - n`.
- **Other reasons an item goes to `work-item history`:** the dossier maps its own iteration field (the feed sends reportable fields, and an empty field and an unreported one look alike); a revision has no `System.ChangedDate`; `System.ChangedBy` is text that is not `Name <email>`; `get-many` did not return the item (no `rev` to check); the feed call itself failed (the failure stays on the work panel, with toil's message, and every item is read as before).
- **The adapter gives `mapOwi` each history as `work-item history` would: an envelope under that command, the item's revisions oldest first, with the feed's `meta.page` and `meta.warnings` dropped.** What is not identical, plainly: the raw revision records. `mapOwi` keeps every record it read under `native`, so an item's `native['ado work-item history']` holds the feed's revisions (text people, `System.Id`, `System.Rev`, no `url`) instead of the history's (identity objects, a `url`). No view reads that key (a history is an array, which readiness and the assignment model skip), and `ui/test/ado-revisions.test.ts` holds the mapped items otherwise equal, `history.transitions` and `history.iterations` included, on the sample's revisions in three shapes: the whole feed, a feed that starts mid-history, and Services-style email addresses against Server accounts. The cache stores the feed's records in `native` where it stored the history's, about the same bytes.
- **Incremental syncs read the feed from the watermark and lay it over the cached feed by item and revision number** (`mergeFeed`), keeping the newer copy of a revision read twice (the watermark's margin makes that common), and dropping items the run's search no longer lists so the cached feed stays the size of the window. It does this only because the result is checked the same way a fresh read is: an item whose merged revisions are not 1 to `rev` is read with `work-item history`. So the merged result is either the same revisions a fresh feed read gives (the test lays a delta with overlap over a cached feed and maps the same items) or the item is read whole. A changed item the feed never held whole (an old open one) still costs its history call each time it changes, which is the old cost; it is not worse.
- **The cache key leaves `updatedSince` out** (`inputKey`, and the sample's `callKey`). The feed's start date moves with the clock, so keyed by it the cached feed could never be found again. The sync records the loader's input and adds its own `updatedSince` to a delta read only, so no earlier cache row carries one. A search or list asked with a different `updatedSince` by hand is not distinguished either; the loader never does that.
- **The daily reconcile is unchanged and stays ids-only.** Deleted items leave the search's cached answer there and, in the same run, the feed's merge.
- **Toil UI from this commit needs a toil with `ado work-item revisions`.** Pinning is unchanged: Toil UI pins `@imagile-dev/toil` exactly and never releases ahead of the toil it needs. Run against the pinned toil (0.1.0-beta.2) the feed call fails with an unknown command on the work panel and the source is marked failed, as `--changelog` does for Jira; a `toil-ui-v…` release goes out with or after the toil release that has it and bumps the pin in the same release PR.
- **Scale** (`ui/test/scale-sim.ts`, 3000 items, 200 live, one live item in four an old open item with six revisions, 200 revisions a batch assumed): first sync 211 toil calls (1 search, 1 get-many, 200 histories) became 62 (1 search, 1 get-many, 1 feed, 50 histories for the old open ones); requests 211 became 64. Second sync with nothing changed 8 calls became 9 (the feed is asked from the watermark and answers nothing). A third sync with one recent and one old open item changed stays 11 calls (histories 2 became 1), and writes more response bytes (317,834 became 455,321) because the cached feed is one row that is rewritten whole when anything in it changes; the Jira slice made the same trade. The win is the first sync; the incremental sync is about level.
- **Not changed, noticed:** the loader sends every id to `get-many` in one call and toil refuses more than 1000 in a call (`work-item get-many`), so a window of more than 1000 Azure DevOps items fails there regardless of this change.
